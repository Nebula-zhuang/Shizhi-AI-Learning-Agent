### 3.4 为什么只建这三张表

| 不建的表 | 理由 |
|---|---|
| `users` | P1 无登录、无任何消费者；建了就是一张空表。P5 引入学习状态时一并建并回填 `document_id → user_id` 的归属关系 |

| `knowledge_checks` | 可信度校验属 P2 |

**克制建表是有意的**：宁可 P2 多加一次迁移，也不在 P1 留下一堆没有写入方的表。

## 4. 统一文档结构（跨模块契约）

解析层的输出、前端原文预览的输入、P3 引用回链的依据，都基于这一个结构：

```json
{
  "document_hash": "sha256:…",
  "file_name": "操作系统原理-第3章.pdf",
  "file_type": "pdf",
  "page_count": 12,
  "pages": [
    {
      "page_no": 1,
      "has_text_layer": true,
      "blocks": [
        {"type": "heading", "text": "3.1 进程的概念", "level": 2, "bbox": [72, 96, 420, 118]},
        {"type": "text",    "text": "进程是程序的一次执行过程……", "bbox": [72, 130, 520, 210]},
        {"type": "figure",  "image_path": "images/p1_0.png", "caption": "图 3-1 进程状态转换",
         "width": 640, "height": 320, "bbox": [140, 240, 480, 400]}
      ]
    }
  ],
  "meta": {
    "parser": "pymupdf",
    "image_count": 4,
    "warnings": [{"code": "NO_TEXT_LAYER", "page_no": 7, "message": "第 7 页无文本层，疑似扫描件"}]
  }
}
```

**约定**：图片只存**相对路径**（`images/p1_0.png`），绝对路径由上层拼接。
落盘位置 `<UPLOAD_DIR>/<file_hash>/images/p{页码}_{序号}.png`。
这样更换存储根目录时无需迁移数据。

结构与分块规则详见 `skills/doc-ingestion/SKILL.md`。

## 5. 摄取流水线（Workflow A 的 P1 切片）

### 5.1 请求与执行分离

```
POST /api/documents
  ├─ 校验扩展名 / 大小(≤30MB) / 页数(≤50)
  ├─ 计算 sha256 → 命中已有文档? → 直接返回既有记录（dedup=true，不重复解析）
  ├─ 落盘 data/uploads/<hash>/source.<ext>
  ├─ 写 documents 记录（status=pending）
  ├─ 投递后台任务
  └─ 立即返回 202 + document（不阻塞请求）

后台任务（asyncio 信号量，并发上限 2）
  ├─ parsing    进度 10→40  解析 → 统一结构落盘 + 图片提取
  ├─ chunking   进度 40→55  分块 → 写入 chunks
  ├─ extracting 进度 55→95  分批抽取 → 去重 → 写入 knowledge_points
  └─ ready      进度 100    回填统计
任一阶段异常 → failed + parse_error + stage_detail
```

### 5.2 状态机

```
pending → parsing → chunking → extracting → ready
              ↘         ↘          ↘
                    failed（记录失败阶段与原因）
```

前端凭 `parse_status` + `progress` + `stage_detail` 展示进度，不猜测。

### 5.3 并发与限流

- 全局 `asyncio.Semaphore(INGEST_MAX_CONCURRENCY=2)`，防止连续上传打爆 LLM 限流。
- **这是进程内轻量执行器，不是消息队列**（你已明确排除 MQ）。
- **已知局限与处置**：进程重启会丢失运行中的任务，文档会卡在中间状态。
  为此在应用启动时做一次 **stale 清理**：把仍处于 `parsing/chunking/extracting` 的文档
  标记为 `failed`，`stage_detail = "服务重启导致中断，可点击重新处理"`，
  用户通过 `/reprocess` 一键重跑。**不留下永远转圈的僵尸文档。**

### 5.4 失败降级原则

**局部失败不得导致整体失败。** 具体：

| 故障 | 处置 |
|---|---|
| 单页解析异常 | 跳过该页 + warning，其余页继续 |
| 单个 chunk 抽取失败 | 重试 1 次 → 仍失败则跳过该批 + warning |
| 整份 PDF 无文本层 | `failed` + 明确提示（疑似扫描件） |
| 文件加密/损坏 | `failed` + 可读错误信息 |
| 知识点引用越界 | 丢弃该条知识点，计数记 warning |

一份 50 页的 PDF，即使有 2 页出问题、1 批抽取失败，**剩下 48 页也必须产出可用知识点**。

## 6. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/documents` | 上传（multipart）。返回 202 或既有记录（去重） |
| GET | `/api/documents` | 文档列表（分页，按创建时间倒序） |
| GET | `/api/documents/{id}` | 详情（统计 + warnings） |
| GET | `/api/documents/{id}/status` | **轻量轮询**：status / progress / stage_detail / kp_count |
| POST | `/api/documents/{id}/reprocess` | 清空 chunks 与知识点后重跑 |
| DELETE | `/api/documents/{id}` | 级联删除 DB 记录 + 磁盘文件 |
| GET | `/api/documents/{id}/structure` | 统一文档结构（含图片相对路径） |
| GET | `/api/documents/{id}/chunks` | chunk 列表（`?page=&limit=`） |
| GET | `/api/documents/{id}/knowledge-points` | 知识点列表（`?difficulty=&order=`） |
| GET | `/api/knowledge-points/{kp_id}` | 知识点详情 **+ 来源 chunk 原文**（回链） |

### 关键响应示例

**上传命中去重**
```json
{ "document_id": 3, "dedup": true, "parse_status": "ready",
  "message": "该文件已于 2026-09-17 10:12 解析过，直接复用" }
```

**轮询状态**
```json
{ "document_id": 3, "parse_status": "extracting", "progress": 72,
  "stage_detail": "正在抽取知识点（第 3/5 批）", "kp_count": 9, "chunk_count": 24 }
```

**知识点详情（回链用）**
```json
{
  "id": 11, "title": "进程与线程的区别",
  "summary": "进程是资源分配的基本单位，线程是 CPU 调度的基本单位。",
  "details": "## 核心区别\n…", "key_points": ["…"],
  "difficulty": 2, "importance": 5, "confidence": 0.95, "verify_status": "unverified",
  "tags": ["操作系统", "并发"], "heading_path": ["第3章 进程管理"],
  "sources": [
    { "chunk_index": 3, "page_start": 2, "page_end": 2, "content": "进程是……" },
    { "chunk_index": 4, "page_start": 3, "page_end": 3, "content": "线程是……" }
  ]
}
```

最后这个 `sources` 字段就是**溯源闭环**：前端点页码 → 展开原文 → 学生能自己核对 AI 有没有讲错。
这是本项目区别于普通 AI 问答的核心，也是 P3 做引用回链的同一份数据。

## 7. 知识点抽取设计（要点）

完整规则见 `skills/knowledge-extraction/SKILL.md`，这里只列会影响评审的关键决策：

| 决策 | 做法 | 理由 |
|---|---|---|
| 批次划分 | 按 `heading_path` 聚合，3–5 块 / ≤4000 字符 | 同章节上下文完整，抽出的知识点内部一致 |
| **页码不由模型输出** | 模型只输出 `source_chunk_indexes`，`source_pages` 由代码反查回填 | 与其在提示词里反复叮嘱"别编页码"，不如让模型**根本没有**输出页码的字段。能靠结构避免的错误，不靠提示词 |
| 去重 | 两层：提示词内传 `existing_titles` 联合去重 + 产出后归一化兜底 + 数据库 `UNIQUE(document_id, title_norm)` 三层 | 提示词挡掉大多数，代码兜住剩下，DB 保证绝不重复 |
| 结构化输出 | `response_format={"type":"json_object"}`，解析容错（剥离围栏 + 提取首个 JSON 对象），失败重试 1 次 | 三家主流服务商均支持；不支持时仍可用 |
| 质量闸门 | 每批自检（数量 1–5、source 非空、区间合法），不合格只标记该批 partial | 不因单批异常中断整份文档 |
| 幂等 | `reprocess` 先清空该文档的 chunks 与知识点再重跑 | 可反复调试抽取提示词，不必手动清库 |

### 7.1 mock 模式增强（可测试性的关键）

P1 的流水线强依赖 LLM，若每次测试都打真实 API，既慢又烧额度。因此扩展 mock 行为：
`chat_json()` 在 mock 模式下**返回由输入派生的合法 JSON**（从 chunk 首句生成 title/summary，
页码由代码正常回填）。

这样整条 P1 流水线**离线可跑、可回归、零 API 消耗** —— P0 的 mock 机制在这里从"验证链路"
升级为"支撑测试"。


### 9.2 两个有意的取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| 是否引入 `react-router` | **不引入** | P1 导航深度只有 2 层，视图状态切换足够。引入路由库增加依赖却不带来实际收益。P4 辅导界面需要深链接（分享某道题）时再评估 |
| Markdown 渲染 | **本轮引入** `react-markdown` + `remark-gfm` | 知识点的 `details` 就是 Markdown；同时顺带修掉 P0 遗留的"`**粗体**` 显示为纯文本"问题。这是 P0 已知问题清单里的第 1 项 |

### 9.3 轮询策略

仅当列表中**存在非终态文档**时，每 2 秒请求一次 `/status`；全部进入 `ready`/`failed` 后**自动停止轮询**。
避免空闲页面持续打接口。

## 13. 风险与待你确认的决策点

### 13.1 已识别的风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 扫描件 PDF 无文本层 | 该类资料 P1 完全用不了 | 明确检测 + 可读提示；OCR 见决策 D1 |
| 抽取质量依赖分块质量 | 分块差 → 知识点碎且乱 | 先做分块单测并用真实教材验证，再调抽取提示词 |
| LLM 调用次数 | 一份 10 页 PDF 约 6–10 次调用 | 批处理 + `existing_titles` 前置去重；mock 模式支撑离线测试 |
| 抽取耗时 | 大文档可能超 60s | 异步 + 进度可见，不阻塞请求；上限 50 页 |
| 进程内任务执行器 | 重启丢任务 | 启动清理 + `/reprocess` 兜底（§5.3） |

### 13.2 需要你拍板的 5 个决策

| # | 决策 | 我的建议 | 影响 |
|---|---|---|---|
| **D1** | 扫描件 PDF 的 OCR | **P1 不做**，只检测并提示 | 若要做，需新增 OCR 依赖与一次完整开发，建议放 P1.5 |
| **D2** | 图片内容理解（多模态识图） | **P1 只做提取与保留**，不做内容识别 | 当前配置的 `deepseek-chat` 是纯文本模型，识图需另配 VL 模型（如 `qwen-vl-plus`）并新增一把 Key。建议放 P2 |
| **D3** | 是否现在建 Tool 注册表 | **不建**，P4 再做 | P1 把抽取实现为 service，但入参出参按 Tool 契约划分，P4 接 Function Calling 时零重构 |
| **D4** | 前端是否引入路由库 | **不引入** | 见 §9.2 |
| **D5** | 上传上限：50 页 / 30MB | 按此执行 | 可调；放宽会增加单次处理时长与失败面 |

## 〇、先说三件影响方案的事实

### 1. `sessions` 表复用不了，必须新建 `conversations`

现有 `sessions` 是 **Tutor 专用**的，字段绑死了：

```
sessions: learner_id, document_id, knowledge_point_id, title, status, action_count
                              ^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^
```

自由学习的一轮对话**没有"唯一知识点"** —— 它可能同时涉及三个知识点、一份上传的文件、和一次联网搜索。

硬塞进去的后果：要么把这两个字段全填 NULL（表意崩塌，查询要到处判空），
要么为了迁就它把自由对话切成"一个问题一个 session"（那就不叫对话了）。

**你自己也强调了「不要把 Conversation、Knowledge、Memory 混成一张表」** —— 这里正好是同一条原则。

### 2. LLM 网关目前**不支持多模态**

```python
# app/core/llm.py
@dataclass
class Message:
    content: str          # ← 只有文本
```

你要求"如果已支持 OpenAI-compatible multimodal message，优先复用"——**它还不支持**。
所以要**扩展**（加一个 `content` 可以是 parts 数组的形式），而不是重写网关。
OpenAI 兼容格式本身是支持 `content: [{type:"text"},{type:"image_url"}]` 的，
改动集中在 `Message` 与消息序列化两处，其余（超时、重试、mock、stream）全不动。

## 二、核心架构决策（每个一句话理由）

### 决策 1：**不造 5 个新 Skill，先把能力做成 Tool，Skill 只写"什么时候用"**

你列的 `general-qa` / `knowledge-synthesis` / `conversation-memory` 本质上不是"可执行单元"，
而是**提示词策略**。把它们做成 Skill 目录，会得到三个只写了一句话的空壳。

**做法**：
- **能力**（可执行）→ 进 Tool Registry：`retrieve_knowledge` / `web_search` / `analyze_file` / `save_knowledge`
- **策略**（何时用、怎么用）→ 写进 **一个** `skills/free-study/SKILL.md`
- **真正值得独立成 Skill 的只有 `web-research`** —— 因为它有一整套内部编排
  （判断时效性 → 生成查询 → 搜索 → 交叉验证 → 处理冲突 → 生成引用 → 失败降级），
  这不是一段提示词能装下的。

这样 Skill 数量从 +5 变成 +2，且每个都有实质内容。

### 决策 2：**路由用"一次 JSON 决策"，不用多轮 function calling**

现有 `tool/registry.py` 的文档里已经论证过：模型只需输出一个 JSON，不引原生 `tools` 参数。
沿用同一套通道 —— 与 P1/P2/P4 一致，且省一轮往返。

### 决策 3：**不引入 MCP。**

如实说明：当前环境**没有可用的 web search MCP 服务**，项目里也从未有过 MCP。
所以 `WebSearchProvider` 先落地 `Mock` + `Real`（Tavily）两个实现，
`MCPWebSearchProvider` 留**接口位**但不实现 —— 将来接入时不改 Agent 核心。

### 决策 4：**对话与学习状态分离**

```
conversations / conversation_messages   → 完整聊天记录
saved_knowledge                          → 用户主动保存的重要知识
learner_kp_states / learner_profiles     → 学习状态（已存在，与 Tutor 共享）
```

呼应你 §13 的要求，也让"自由学习"和"Tutor"能共享长期状态。

## 五、Free Study Agent 路由

### 一轮的处理流程

```
用户输入（文字 + 可选附件）
        ↓
① 附件已就绪？ 未就绪 → 后台继续处理，先回答能回答的部分
        ↓
② 一次 JSON 决策（复用 chat_json）
    输入：用户问题 + 有没有附件 + 知识库规模 + 联网是否可用
    输出：{"capabilities": ["retrieve_knowledge","web_search"],
           "reason": "…", "needs_time_sensitive": true}
        ↓
③ 按决策并发执行能力（工具层管预算/超时）
        ↓
④ 拼上下文 → 一次 LLM 生成（SSE 流式）
        ↓
⑤ 落库 + 推引用
```

**关键约束（沿用你 §5 的"优先最短路径"）**：

| 问题类型 | 调用次数 |
|---|---|
| 普通知识问答 | 决策 1 次 + 生成 1 次（**不检索、不联网**） |
| 资料问题 | 决策 + 检索 + 生成 |
| 时效问题 | 决策 + 搜索 + 生成 |
| 闲聊/寒暄 | **直接生成**（跳过决策，省一次调用） |

**单轮上限**：工具调用 ≤ 3、总时长 ≤ 30s（与现有 Tutor 一致，直接复用 `registry` 的预算机制）。

### 什么时候**不**联网

沿用已有闸门思路，但更保守：
- 问的是稳定常识（"什么是 JVM"）→ **不联网**
- 问的含时效词（"现在/最新/今年/25 版"）或明显是新事物 → **联网**
- 拿不准 → 不联网，但**在回答里说明"这条我没有联网核实"**

**不联网时绝不说"我查过了"** —— 这条规矩在 `verify_voice.py` 里已经立过，这里沿用同一原则。

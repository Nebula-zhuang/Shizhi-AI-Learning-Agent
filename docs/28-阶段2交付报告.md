## 一、Agent Loop（新增 `app/agent/runtime_loop.py`）

```
OBSERVE → DECIDE → 要调工具? ──yes──→ EXECUTE → OBSERVE_RESULT ──┐
   ↑                  │                                          │
   │                  no                                         │
   │                  ↓                                          │
   └─── 达到上限 ─── FINAL_ANSWER ←──────────────────────────────┘
```

**与 P4 Runtime 的关系**：并存。P4 的九态线性状态机 `DECIDE_ACTION` 一轮只执行一次 ——
那是**刻意设计**（教学动作一轮只能选一个），不是没写完。把工具循环塞进去会让
"教学策略"和"工具编排"互相牵制。`runtime.py` **一行未改**。

### 三条硬限制（实测全部生效）

| 限制 | 默认 | 少了它会怎样 |
|---|---|---|
| `MAX_STEPS` | 6 | 模型可反复"不调工具也不回答"，空转 |
| `MAX_TOOL_CALLS` | 3 | 一步里并发调多个工具，成本失控 |
| `TOTAL_TIMEOUT` | 30s | 每次调用都快但次数多，用户干等 |
| `MAX_RETRY_PER_TOOL` | 2 | 同一工具反复撞墙（**这条是实测后加的**，见 §6） |

**超限不报错，降级到 `FINAL_ANSWER`** —— 与 P4"无论如何都给用户一个回复"一致。

⚠️ **`TOTAL_TIMEOUT` 不约束最终生成**，这是刻意的：生成**就是**降级目标，
给它设时限超时后就什么都输出不了。所以 30s 应理解为"愿意在**工具编排**上花多久"。
实测一个"检索 → 判断 → 联网 → 判断"的完整回合约 32s（编排约 28s + 生成约 4s）。

## 二、Tool Registry（新增 `app/agent/tools/specs.py`）

```
registry.py  「怎么调」—— 预算 / 超时 / 异常包装（ToolRunner、ToolBudget，**原样复用**）
specs.py     「有哪些、叫什么、什么时候能用」—— ToolSpec / ToolRegistry / ToolResult
```

分开的理由：预算规则很少动，而工具集合每个阶段都在加。混在一起会让"加一个工具"
变成"改一个 300 行的文件"。

**四个 Tool**，全部是对既有能力的薄包装（**没有实现任何新能力**）：

| Tool | 复用 |
|---|---|
| `retrieve_knowledge` | P3 的 `rag_service.retrieve_knowledge` |
| `web_search` | Provider（本阶段加了 MCP 后端） |
| `document_analysis` | 同一个检索，限定到指定资料 |
| `image_analysis` | LLM 网关的多模态通道 |

**`ToolResult.content` 是文本不是 JSON** —— 模型读结构化 JSON 时容易把字段名
当内容讲出来（"根据 url 字段…"）。结构化的部分放 `display`，那是给界面看的。

**`available_specs()` 与 `names()` 刻意分开**：联网没配时 `web_search` 不该进
给模型的清单 —— 让它看见一个调不通的工具，只会浪费一次决策。

## 三、MCP 接入（新增 `app/search/mcp_client.py`）

### 用哪个

**Tavily 官方 MCP Server** —— `tavily-ai/tavily-mcp`，**复用现有 `TAVILY_API_KEY`**（不新增密钥）。

### 实测跑通的协议链

```
POST https://mcp.tavily.com/mcp/     Authorization: Bearer <TAVILY_API_KEY>

① initialize  → serverInfo {"name":"tavily-mcp","version":"4.0.4"}  协议 2025-06-18
② tools/list  → 5 个工具
③ tools/call  → tavily_search("Java 25 virtual threads") → isError:false
```

**响应是 SSE 包装的**（`event: message\ndata: {...}`），要剥壳 —— 但也要认裸 JSON，
不能假死后一种。

### ⚠️ 工具名必须动态发现（这是实测出来的硬教训）

| | 工具名 |
|---|---|
| 官方 README / 各 MCP 目录站 | `tavily-search`（**连字符**） |
| `tools/list` **实际返回** | `tavily_search`（**下划线**） |

**照文档硬编码，功能会静默不工作**，报错是一句难懂的 "tool not found"。

所以 `pick_search_tool()` 是**唯一的"名字形状知识"所在地**：
按**分词后的 token** 打分（`search` +10、`web` +3），并排除
`extract / crawl / map / research / fetch`。

`tavily_research` 是必须排除的一个 —— 它的名字里含 "search" **子串**，
但它是"做一份研究报告"，比一次搜索贵得多。纯子串匹配会误选它。

### 三条回退规则（`WEB_SEARCH_BACKEND=auto` 默认）

| 情况 | 行为 |
|---|---|
| MCP 运行时故障（连不上 / 401 / 超时） | **回退** Tavily，**并上报** `fell_back` + `fallback_reason` |
| MCP 连上了但**清单里没有搜索工具** | ⚠️ **不回退** —— 这是配置/兼容性错误 |
| `mcp` 模式 | 失败就失败，**不偷偷换**（便于验证 MCP 真的在工作） |
| `tavily` 模式 | **一次 MCP 请求都不发**（有测试断言） |

**第二条是刻意的**：配置错误是确定性的。静默回退会把"工具名对不上"
永远掩盖成"网络偶尔不好" —— 你会一直以为 MCP 在工作，直到某天 Tavily 也挂了。

## 五、三个 Agent E2E

### A. 普通问题 → 无工具 → 直接回答 ✅

```
"什么是 JVM？"
事件: {status: 2, delta: 56, done: 1}   工具调用 0 次   耗时 6.8s
```

走**启发式快通道**（没提资料、没时效信号 → 不调决策模型）——
保住你要求的"简单问题一次 LLM 调用"。

### B. 资料不足 → 检索 → 再判断 → **MCP 联网** → 再判断 → 回答 ✅

```
"根据我的资料讲讲虚拟线程，资料里没有的再联网查"

step 1: DECIDE  tool=retrieve_knowledge  ok=True
step 2: DECIDE  tool=web_search          ok=True     ← 循环的证明
step 3: DECIDE  tool=None                            ← 收尾

工具调用序列: ['retrieve_knowledge', 'web_search']
provider=mcp | fell_back=False | 引用 7 条（网页 5）
```

**流水线做不到这件事** —— 它只能按预先写好的顺序跑。

浏览器里右侧面板可见：`1. 翻了你的资料 → 2. 联网查了`，且联网那步标着**经由 MCP**。

### C. 图片 → image_analysis → 再判断 → 回答 ⚠️ **有保留**

**多模态链路已通，但当前配置的模型不支持视觉。**

实测证据：图片按 OpenAI 多模态格式发给当前模型（DeepSeek），
**接口不报错**，但模型回一句"我无法查看或分析图片"。

这种"不报错但也没看图"的情况特别危险：工具会返回 `ok=True`，
Agent 拿到一个没用的结果**白转 4 轮**（第一次实测就是这样）。

**处理方式**（我认为这是正确的做法）：

1. 加了显式能力开关 `LLM_SUPPORTS_VISION`（默认 `false`）
2. 关掉时 `image_analysis` **不进给模型的清单** —— 不让它去调一个注定失败的工具
3. 附件提示词改成"当前模型不支持看图，请如实告诉用户"，**而不是让它去猜图里有什么**

实测降级行为：0 次工具调用、4.3s、回答如实说"我看不了图，请把代码贴出来"。

**要真正跑通场景 C**：把 LLM 换成支持视觉的模型（Qwen-VL / GPT-4o / GLM-4V 等），
然后设 `LLM_SUPPORTS_VISION=true`。代码路径已就绪并有测试覆盖。

## 六、实测踩到并修掉的四个真 bug

写这个阶段最大的收获其实是这些 —— 它们都不是"想"出来的，是跑出来的。

### ① 模型自己发明工具名

用户传图问"这段代码什么意思"，模型没用清单里的 `image_analysis`，
而是**自己编了一个 `extract_text_from_image`** —— 不存在，调用失败，然后说"我看不到图"。

**修**：决策提示词加两条硬规矩 + 附件块从"陈述事实"改为"给出下一步"。

### ② 同一工具反复失败，提示词拦不住

提示词里写了"同一个工具最多试两次"，模型**仍然连续 4 次**调用同一个失败的工具。

**修**：`MAX_RETRY_PER_TOOL` 写进代码强制执行。
**涉及成本与时间的限制，代码是唯一的执行者** —— 提示词只能起引导作用。

### ③ 缺必填参数直接抛 TypeError

模型返回 `{"document_ids": [...]}` 却没有 `query`，
直接调用抛 `TypeError: missing 1 required positional argument: 'query'`。
那句报错对模型毫无帮助（它不知道该补什么），对人也不好排查。

**修**：调用**之前**校验必填参数，返回一句可执行的话（"少了 query，它的参数是…"）。

### ④ 换个说法重复调同一个工具，把额度用光

用户说"资料里没有的再联网查"，模型却把检索词换了三次
（`虚拟线程` → `虚拟线程 OR Project Loom` → …），**三次额度全花在检索上，
一次都没轮到联网**。

**修**：两层。
- 提示词：加一节"最常犯的错"，判据是"这次调用会拿到新信息吗"
- 代码：`overused_tools()` 把"这个工具已调 N 次且都成功"作为**事实**注入决策，
  **代码给事实，模型做判断**

修完后序列变成 `retrieve_knowledge → web_search` ✅

## 九、多模态（`app/core/llm.py`）

```python
Message = dict[str, Any]        # 原来：dict[str, str]
```

**扩宽类型的值，不是改结构** —— OpenAI 兼容的多模态格式本身就是
`content` 可以是 parts 数组，不需要造新的消息类型。

```python
user_message("这张图是什么？", [data_uri])   # 组装

message_images(msg)                          # 取图片
```

⚠️ 踩坑：`_last_user_question` 与 `_stream_mock` 原来直接
`(msg.get("content") or "").strip()` —— 多模态时 content 是 list，会 AttributeError。
已全部改走 `message_text()`。

**P1–P6 与 Tutor 的调用点一行未改** —— 它们传的仍是纯文本，走的仍是老分支。

### ⚠️ 一个环境层的脆弱点（如实说明）

验证过程中遇到过一次 `attempt to write a readonly database`。

**根因是我的测试方法**：我在服务器持有 Chroma(SQLite) 的同时，
又跑了直接访问同一个 store 的脚本 —— Chroma 的 SQLite 后端不支持多进程并发写。

**不是产品 bug**，但它揭示了一个真实的脆弱点：
**如果生产部署里有两个进程访问同一个 `data/chroma`，检索会间歇性失败**，
而且报错（"readonly database"）很难联想到"并发访问"。
部署时应当保证单写者。

# 上传上限扩容到 300MB · 交付报告

> 日期：2026-09-20
> 需求：PDF / Word / MD 上传大小扩到极限 300MB，然后重新部署

---

## 〇、一句话结论

**上限改成了 300MB，但这不是"改一个数字"。** 真正的工作量在三处：

1. **改成流式落盘** —— 原先是整份读进内存，300MB 下单次上传就常驻 300MB+，并发几个直接 OOM
2. **发现并修复了一个真 bug** —— 我新写的清理代码会**吞掉原始错误**，把"文件超限"变成 500
3. **补上了解析容量闸门** —— 上传上限和解析能力是**两个不同的限制**，只抬前者会造成"文件收下了，然后磨六个小时"

---

## 一、上限到底在哪儿生效

第一个坑：**`config.py` 里的默认值不是生效值。**

```python
# app/core/config.py
max_upload_mb: int = 30    ← 改了这里没用
```

```bash
# .env  ← 真正生效的地方
MAX_UPLOAD_MB=30
```

`.env` 覆盖了代码默认值。只改代码的话，重启后你会看到"还是 30MB"。
已同时改 `.env` 与 `.env.example`（都加了说明性注释）。

---

## 二、核心改造：整份进内存 → 流式落盘

### 原来的流程

```python
data = await file.read()          # 300MB 进内存
validate_upload(data)             # 再读一遍（PDF 探测）
file_hash = compute_hash(data)    # 又读一遍
store_source(data)                # 第三遍，写盘
```

内存峰值 ≈ 文件大小的 2–3 倍。30MB 时代无所谓，300MB 就是事故。

### 现在的流程

```python
temp, size, digest = await storage.stream_to_temp(chunks, max_bytes=...)   # 边收边写边算哈希
validate_upload(temp, file_name=..., size=size)   # 从**路径**读，PyMuPDF 按需取
storage.finalize_source(temp, digest, file_name)  # os.replace 原子改名归位
```

内存占用固定在 **1MB 量级**（`UPLOAD_CHUNK`），与文件大小无关。

### 几个刻意的设计

| 决定 | 理由 |
|---|---|
| **超限时边写边判** | 不能先把 5GB 写完再拒绝 —— 既浪费磁盘也浪费用户上传的时间 |
| **哈希在写入过程中算** | 去重判断不该再把 300MB 读第二遍 |
| **中转目录放在 `upload_root()` 里面** | 同一文件系统 → `os.replace` 是原子改名（瞬间完成），而不是跨盘复制 300MB |
| **`os.replace` 而不是读出来再写** | 中途断电不会留下半个文件 |
| **启动时清理 `.part` 残骸** | 进程被强杀时 `discard_temp` 不会执行，300MB 级残骸很占地方 |

## 三、修掉一个我自己写出来的真 bug

第一次实测 320MB 时返回的是 **500 而不是 413**。看栈才发现问题在我自己的代码里：

```python
except BaseException:
    target.unlink(missing_ok=True)   # ← 这行自己抛了异常
    raise
```

**清理动作抛的 `OSError` 把原始的 `UploadTooLarge` 覆盖掉了。** 用户看到的是 500，
而不是"文件超过 300MB 上限"那句能看懂的话。

这不是本机特有的问题：Windows 上杀毒软件占着文件句柄、网络盘暂时不可用，
都会让删除失败。**清理是"尽力而为"的收尾动作，它失败不该改变主要结论。**

已改成走 `discard_temp()`（它吞掉 `OSError` 只记日志），并补了两条测试钉住这个不变量：
- 清理失败时，原始异常必须原样抛出
- `discard_temp` 遇到删除失败绝不能往上抛

## 四、一个更重要的发现：上传上限 ≠ 解析能力

实测 35MB 的 Markdown 时，进度显示：

```
正在抽取知识点（第 1/5398 批）
```

**5398 批意味着要调 5398 次模型**，并发 2 也要几个小时，还会烧掉大量 API 配额。

### 两个限制的区别

| 限制 | 管什么 | 现状 |
|---|---|---|
| `max_upload_mb` | 传输能不能**收下**这个文件 | 300MB |
| `max_document_pages` | PDF 解析**页数** | 已有，50 页 |
| `max_extract_batches` | 收下后要调**多少次模型** | **本次新增**，300 批 |

**PDF 一直是安全的** —— 50 页的闸门挡着。而一个 300MB 的扫描件通常是
"页数少、体积大"，正是大文件上传的真实用途，这条路完全走得通。

**漏洞在 docx / md / txt** —— 它们没有页数概念，也就没有任何等价闸门。
35MB 纯文本 → 21,589 个文本块 → 5,398 批。

### 补的闸门

在分块之后、**写库之前**判断（否则会先把两万行写进库再失败，白占空间）：

```python
batches = (len(drafts) + settings.extract_batch_chunks - 1) // settings.extract_batch_chunks
if batches > settings.max_extract_batches:
    raise ParserError("…超过单文档处理上限 300 批。请拆分后再上传。", code="TOO_MANY_CHUNKS")
```

**选择"明确拒绝"而不是"静默截断"**：截断意味着用户的教材只被读了一半，
而界面上显示"处理完成"—— 那比拒绝有害得多。

## 五、前端

### 上传进度（XHR）

`fetch` 至今没有可用的上传进度事件。300MB 的文件如果几十秒没有任何反馈，
用户会以为卡死然后重复点击。所以上传路径改用 `XMLHttpRequest`
—— 这是标准里唯一能拿到 `upload.onprogress` 的手段。

错误语义与 `fetch` 路径保持一致（同样提取 `detail` 抛成 `Error.message`），
两条路径不会给出两种措辞。

### 前置大小校验

```ts
export const MAX_UPLOAD_MB = 300   // 必须与后端 .env 一致
export function checkUploadSize(file: File): string | null
```

前端也存一份的理由不是"双重保险"，是**体验**：后端要收完整份才知道超限，
传一个 500MB 的文件再被拒是白等几十秒。

**刻意不自动压缩**：静默改小用户的文件比拒绝更糟 ——
他以为传上去的是原件，实际解析结果会莫名其妙地不完整。

### Vite 代理超时

`timeout` / `proxyTimeout` 放宽到 10 分钟。默认值对普通 JSON 请求够用，
但 300MB 的请求体在慢盘上可能超过默认值，表现为"传到一半莫名中断"。

## 八、需要你知道的

1. **300MB 是"传输上限"，不是"能学会的上限"。**
   一份 300MB 的扫描件 PDF 只要不超过 50 页就能正常处理；
   但如果你传一份几十 MB 的纯文字讲义，它会在切分后被闸门拦下并告诉你拆分 ——
   这是有意的，因为逐批调模型抽取知识点是真的要花几个小时。

2. **数值三处必须一致**：后端 `.env` 的 `MAX_UPLOAD_MB`、
   前端 `library.ts` 的 `MAX_UPLOAD_MB`。不一致会出现"前端放行、后端 413"。

3. **本机启动后端请清掉 `PYTHONPATH`**：
   宿主注入的删除拦截会让"清临时文件"失败（代码已容错，但会留残骸）。
   启动命令：`PYTHONPATH="" python -m uvicorn app.main:app ...`

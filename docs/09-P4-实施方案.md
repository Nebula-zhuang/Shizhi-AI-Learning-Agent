## 一、先说两处与需求假设不符的地方

这两点必须在动手前讲清楚，否则做出来的东西会与预期错位。

### 不符 1：`learner_kp_states` / `sessions` / `messages` / `answer_evaluations` **都不存在**

需求里写的是「优先复用现有 …… 等表」。但实际数据库只有 7 张表：

```
alembic_version  app_meta  chunks  documents
knowledge_checks  knowledge_points  knowledge_relations
```

`docs/01-技术方案-v1.md` 的 ER 设计里有那四张表，但 P0 的迁移文档明确写了
「`users` —— P1 无登录、无消费者，建了就是空表（P5 再建）」，
学习相关的表同理被推迟到了 P4。

**处置**：用 **Alembic 0004 新建**这四张表（符合"如需改表使用 Alembic"），
字段严格按 `docs/01` 的 ER 设计 + 需求里点名要求的字段名。

### 不符 2：`get_learner_state` / `generate_question` / `evaluate_answer` / `update_learning_state` **都不存在**

需求写的是「缺失时再补充，不要重复实现」。实际只有 `retrieve_knowledge` 的能力存在
（P3 的 `rag_service.retrieve`）。所以：

| 工具 | 现状 | 处置 |
|---|---|---|
| `retrieve_knowledge` | ✅ P3 已有 | **包装复用**，不重写 |
| `get_learner_state` | ❌ 不存在 | 新建（`learner_service`） |
| `update_learning_state` | ❌ 不存在 | 新建（`learner_service`） |
| `evaluate_answer` | ❌ 不存在 | 新建（`assessment_service`，按需求的结构化输出） |
| `generate_question` | ❌ 不存在 | 新建（`assessment_service`） |

`app/agent/` 目录有 `prompts/ tools/ workflows/` 三个子目录，但**只有 `__init__.py` 占位**
（P0 只留了骨架），所以「现有的 Lightweight Agent Runtime」是**要新建**的，
不是复用。`__init__.py` 里写的规划（`runtime.py` / `policy.py` / `tools/`）正好是本阶段的实施内容。

### 一处需要说明的取舍：`learner_id` 用字符串，不建 `users` 表

需求要求 Learner State 保存 `learner_id`。技术方案里是 `user_id` 外键指向 `users` 表，
但**用户体系属于 P5**（P0 就明确推迟）。现在建 `users` 表会得到一张空表，
而且没有登录入口，`user_id` 无处可来。

**处置**：`learner_id` 用 `VARCHAR(64)`，默认 `"local"`（本机默认学习者）。
这样 P4 能独立跑通，P5 加 `users` 表时只需加一列外键并迁移，不会返工。

## 二、数据层（Alembic 0004，四张新表）

### 2.1 `learner_kp_states` —— 学习状态（长期记忆的核心）

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| learner_id | VARCHAR(64) | 需求指定的字段名。**不是外键**（users 属 P5） |
| knowledge_point_id | BIGINT FK→knowledge_points CASCADE | |
| mastery | DECIMAL(4,3) | **0~1 掌握度**，由 Policy 增量更新 |
| attempt_count | INT | 累计作答次数 |
| correct_count | INT | 累计答对次数 |
| consecutive_correct | INT | **连续答对** —— 驱动升难度的直接依据 |
| consecutive_wrong | INT | **连续答错** —— 驱动换讲法/降难度的直接依据 |
| last_error_type | VARCHAR(30) | 上次错因，供"换讲法"对症下药 |
| status | VARCHAR(16) | new / learning / weak / mastered |
| last_attempt_at | DATETIME | |
| updated_at | DATETIME | |

唯一索引 `(learner_id, knowledge_point_id)`。

> `mastery` 用 `DECIMAL(4,3)` 而不是 `(3,2)`：`(3,2)` 只能表示 0.00–9.99，
> 虽然够用但语义不清；4 位精度能表达 0.001 的增量，避免小增量被四舍五入抹平
> （曾出现的坑：一次 +0.004 的更新被 `(3,2)` 舍入成 0，看起来像"状态没更新"）。

### 2.2 `sessions`

`id` / `learner_id` / `document_id` FK / `knowledge_point_id` FK / `title` /
`status`(active/finished) / `action_count` / `created_at` / `last_active_at`

> 技术方案的 `sessions` 只有 `document_id`。P4 的会话是**围绕某个知识点**展开的，
> 加 `knowledge_point_id` 让"这个会话在学什么"一目了然，也便于按知识点查历史会话。

### 2.3 `messages`

`id` / `session_id` FK / `role`(user/assistant/system) / `content` /
**`action_type`**（记录 Agent 决策结果）/ `kp_ids` JSON / `refs` JSON（RAG 来源）/
`reason`（决策理由）/ `state_snapshot` JSON（决策时的学习状态快照）/ `created_at`

> 加 `reason` 与 `state_snapshot` 是刻意的：演示要证明"Agent 根据学习状态改变策略"，
> 就必须能回放出**当时的状态是什么、为什么选了这个动作**。
> 只存一句"讲了一句话"是证明不了的。

### 2.4 `answer_evaluations`

`id` / `session_id` FK / `message_id` FK（评估的是哪条回答）/ `knowledge_point_id` FK /
`question` / `user_answer` / `correct` BOOL / `score` DECIMAL(4,3) /
`confidence` DECIMAL(4,3)（**评估本身的把握，与 mastery 严格区分**）/ `level`
(not_mastered/vague/mastered) / `error_type` / `missing_points` JSON /
`misunderstood_points` JSON / `feedback` TEXT / `engine` / `created_at`

## 三、Policy：阈值全部在代码里

### 3.1 六个动作与触发条件

**优先级从高到低**（顺序本身就是设计，必须固定下来，否则规则会互相打架）：

| # | 条件 | 动作 | 含义 |
|---|---|---|---|
| 1 | `mastery >= 0.85` | `summarize` | 达到掌握阈值 → 收束总结 |
| 2 | `consecutive_wrong >= 3` | `easier` | 连错三次 → 降难度（回到更基础的表述） |
| 3 | `consecutive_wrong >= 2` | `rephrase` | 连错两次 → 换讲法 |
| 4 | 本轮答对但**浅** | `probe` | 答对没答透 → 追问逼深 |
| 5 | `consecutive_correct >= 2` | `harder` | 稳定答对 → 升难度 |
| 6 | 本轮答错且 `mastery < 0.40` | `explain` | 基础薄弱 → 重新讲解 |
| 7 | `attempt_count == 0` | `explain` | 初次接触 → 先讲再问 |
| 8 | 其它 | `probe` | 默认追问 |

「浅」的判定：`score < 0.70` 或评估出的 `level == 'vague'`。

**为什么规则 4 排在规则 5 前面**：一个学生连续答对但每次都答得很浅，
此时加难度只会让他更懵；先把浅的地方问透才是对的。
这条顺序是**刻意的**，有专门的测试守着。

### 3.2 硬阈值不可被 LLM 覆盖

```
       ┌──────────────────────────────────────────┐
       │ Policy.decide(state, assessment)          │
       │  → 命中规则 1/2/3/5/7 时，动作被强制锁定    │
       │  → 否则给出「允许集合」，交给 LLM 在集合内选 │
       └──────────────────────────────────────────┘
                          ↓
       ┌──────────────────────────────────────────┐
       │ LLM 输出 {action, kp_id, reason, confidence}│
       └──────────────────────────────────────────┘
                          ↓
       ┌──────────────────────────────────────────┐
       │ Policy.validate(决策) —— 最后一道闸门      │
       │  action 不在允许集合 → 丢弃，用 Policy 默认值 │
       │  kp_id 不属于本会话  → 丢弃                  │
       │  confidence 越界     → 截断                  │
       └──────────────────────────────────────────┘
```

**分工**：Policy 管"硬约束"，LLM 管"自由区里的选择与措辞"，Policy 再校验一次。
这样既保证阈值不被模型自己定义，又保留了 Agent 的决策能力（`reason` 由模型给出）。

### 3.3 mastery 增量公式（也在 Policy 里）

```python
# 答对：越接近掌握，增益越小（渐进逼近 1，不会一次跳满）
mastery += LEARN_GAIN (0.35) * score * (1 - mastery)

# 答错：按"当前掌握程度"比例回退（本来就不熟的知识掉得少）
mastery -= WRONG_PENALTY (0.30) * (1 - score) * mastery
```

两条都有上下界钳制在 `[0, 1]`。这个公式实测约 **5–6 次答对**能把 mastery 从 0 推到 0.85，
正好够演示一个完整的学习闭环，不会长得让人失去耐心。

### 3.4 `mastery` 与 `confidence` 严格区分

| | mastery | confidence |
|---|---|---|
| 是什么 | **学习状态**：这个学习者对这个知识点掌握到什么程度 | **评估质量**：本次"判对/判错"这个结论本身有多可信 |
| 谁来写 | Policy 的增量公式 | LLM 结构化输出 |
| 存放 | `learner_kp_states.mastery` | `answer_evaluations.confidence` |
| 用途 | 决定教学动作 | 低时提示"本次评估把握不大，建议人工复核" |
| 生命周期 | 跨会话累积 | 一次评估一条 |

代码里两者**不共用任何变量名**，并有测试断言"confidence 不参与 mastery 计算"。

## 四、Tutor Runtime 状态机

```
LOAD_STATE → RETRIEVE → DECIDE_ACTION → EXECUTE_ACTION → WAIT_USER
                                                              ↓
                    NEXT_TURN ← UPDATE_STATE ← ASSESS ← ───────┘
```

每个状态做且只做一件事：

| 状态 | 动作 | 失败降级 |
|---|---|---|
| `LOAD_STATE` | `get_learner_state(learner_id, kp_id)` | 查不到 → 视为全新状态（mastery=0） |
| `RETRIEVE` | `retrieve_knowledge(question, kp_id)` 复用 P3 | **失败/无结果 → 不带资料继续**（记 warning） |
| `DECIDE_ACTION` | Policy 硬规则 + LLM 决策 + Policy 校验 | LLM 失败/超时 → 用 Policy 的默认动作 |
| `EXECUTE_ACTION` | 生成该动作对应的教学内容/题目 | 生成失败 → 用该动作的兜底模板 |
| `WAIT_USER` | 交还控制权，返回本轮结果 | — |
| `ASSESS` | `evaluate_answer(...)` | LLM 失败 → 启发式评估并标记 `engine=fallback` |
| `UPDATE_STATE` | `update_learning_state(...)` | 事务回滚 → 本轮标记 `state_updated=false`，**不假装成功** |
| `NEXT_TURN` | 回到 `LOAD_STATE` 开始下一轮 | — |

**跨请求**：`/start` 跑 `LOAD_STATE … EXECUTE_ACTION → WAIT_USER`；
`/answer` 跑 `ASSESS → UPDATE_STATE → NEXT_TURN`（即再走一遍到 `EXECUTE_ACTION`）。
状态本身不落库 —— 它完全由 `learner_kp_states` + `messages` 推导得出，
因此不存在"存的运行态与实际数据不一致"这种问题。
但**每轮的流转轨迹会随响应返回**（`trace: ["LOAD_STATE","RETRIEVE",...]`），
便于演示与测试断言"状态机真的按这个顺序走了"。

### 预算与降级（硬约束）

- **每轮最多 3 次 Tool Call**：计数器在 runtime 里，超出直接拒绝并记 warning；
- **每轮最多 30 秒**：每进入一个状态前检查剩余预算，不足则跳过非必需步骤
  （先跳 `RETRIEVE`，再跳 LLM 决策，保证"无论如何都能给用户一个回复"）；
- RAG / LLM / 评估任一失败都不会让整轮失败 —— 每层都有降级路径。

## 五、Tool 层

```
app/agent/tools/registry.py
  TOOLS = { "get_learner_state": Tool(...), "retrieve_knowledge": ...,
            "generate_question": ..., "evaluate_answer": ...,
            "update_learning_state": ... }
  async def call_tool(name, budget, **kwargs)  # 统一走预算与异常包装
```

用**结构化输出（JSON）而非原生 function calling**：模型只需按 schema 输出一个 JSON，
少一轮往返，也不会因为供应商对 tools 参数支持不一致而出问题。
这与 P1/P2 已在用的 `chat_json` 完全一致 —— **复用既有通道，不引新协议**。

## 六、Prompt（3 个文件）

| 文件 | 职责 |
|---|---|
| `tutor_decision.md` | 输出 `{action, knowledge_point_id, reason, confidence}`；**只做选择与解释** |
| `answer_assessment.md` | 输出 `{correct, score, confidence, level, error_type, missing_points, misunderstood_points, feedback}` |
| `tutor_actions.md` | 六个动作各自的生成指令（probe/explain/rephrase/harder/easier/summarize 六节） |

**三个 Prompt 里都不写任何数值阈值。** `tutor_decision.md` 里明确告诉模型
"允许的动作集合由系统给出，你只能在其中选择，不要自行判断难度该不该升"。
阈值只存在于 `policy.py`。有测试守着"prompt 文件里不出现阈值数字"。

## 四、本阶段发现并修复的 2 个真实缺陷

### 缺陷 1：重跑接口静默失败（严重）

**现象**：`POST /api/documents/{id}/reprocess` 返回 503，文档立刻变成 `failed`，
错误信息只有一句含糊的「服务当前无法接收处理任务，请稍后重试」，耗时 0.1 秒。

**根因**：该路由被写成同步函数 `def reprocess_document(...)`。
FastAPI 会把同步路由放进**线程池**执行，而线程池里**没有运行中的事件循环**，
`ingest_runner.submit()` 内部的 `asyncio.create_task` 抛 RuntimeError 并返回 False。
上传路由是 `async def` 所以一直正常，只有重跑接口中招。

**修复**：
1. 改为 `async def`，并在 docstring 里写明原因，避免以后又被"顺手"改回同步。
2. `ingest_runner.submit()` 的错误日志补上「请确认调用方是 async def 路由」的提示。
3. 新增回归用例 `test_reprocess_actually_dispatches_task`。

**更值得记录的是测试为何没拦住它**：我原先的夹具把 `ingest_runner.submit` 打桩成
「永远返回 True」，于是 13 个 API 测试全绿却完全掩盖了这个故障。
修法是**改为打桩流水线本体 `run_pipeline`、保留真实的 `submit`** —— 这样"投递"这一环
重新进入测试覆盖范围，同步路由的问题会立刻暴露。夹具的注释里也写下了这段教训。

> 教训：**把被测环节本身打桩，等于把该环节的 bug 请出测试**。

### 缺陷 2：抽取零产出时没有任何可操作的提示

**现象**：一份文本层损坏的 PDF，解析"成功"、分块"成功"、每批抽取"成功"（返回合法 JSON），
最终 0 个知识点。用户在界面上只看到一个空列表，无从判断是自己资料的问题还是系统的问题。

**根因**：缺少两类检查 —— 解析层不检测文本是否可读，抽取层不检测整篇是否零产出。

**修复**（两处，互相配合）：
1. 解析层新增 `SUSPECT_TEXT_LAYER` 警告：可读字符（汉字/字母/数字）占比低于 50% 且
   文本长度 ≥50 时告警，并给出实际占比。
2. 抽取层新增 `NO_KNOWLEDGE_POINT` 警告：整篇零产出时说明批次数、可用块数与常见原因。

现在同样的坏文件会明确提示「提取出的文字中可读字符仅占 3%，疑似文本层损坏或字体缺少字形映射」。

新增 6 项测试覆盖该检测（`tests/ingestion/test_text_quality.py`），
两个 Skill 文档也同步补上了对应规则。

### 附带说明：这个缺陷是被"假故障"引出来的

> 第一次跑真实 E2E 时，我生成的测试 PDF 用默认西文字体写中文，母语字符没有字形，
> 提取回来全是 `·`，模型正确地返回了空数组。**这是模型行为正确、而我的样本错误**。
>
> 但它恰好暴露了上面这两个真实缺陷 —— 因为如果没有这次意外，我不会想到去检查
> 「有文本层 ≠ 文本可用」。修正样本后（改用 CJK 字体）复测，19 个知识点全部正常产出。

## 六、已知问题与限制

| # | 问题 | 性质 | 说明与建议 |
|---|---|---|---|
| 1 | **Chroma 显示 degraded** | **环境** | `data/chroma/chroma.sqlite3-journal` 被外部进程（宿主程序）独占，SQLite 因此报 `attempt to write a readonly database`。**代码路径已用独立目录验证完全正常**（初始化/写入/读取/清理全通过）。解法：关闭占用该文件的程序后删除 `data/chroma` 目录并重启后端，Chroma 会自动重建。P1 不使用向量库，不影响本阶段功能 |
| 2 | 跨页块的页码精度 | 设计取舍 | 若一个块跨越 3 页，引用它的知识点会标注 3 个页码（如「死锁的定义」标 6/7/8 页）。**不算错**（该块确实覆盖这几页），但不够精确。P3 引入向量检索后可在 chunk 内记录字符偏移，把页码精确到单页 |
| 3 | 扫描件 PDF 不支持 | 按 D1 决策排除 | 检测到无文本层时明确提示「疑似扫描件，P1 未启用 OCR」，不会静默失败 |
| 4 | 图片内容不理解 | 按 D2 决策排除 | 图片被提取保留并登记页码，但不识别内容（需多模态模型）。已在解析提示中告知用户 |
| 5 | 前端溯源原文区未截图留证 | 验证手段限制 | 该区域位于侧栏内部滚动区，自动化工具无法滚动到其位置。**已通过 API 与代码双重验证**：接口返回 `sources` 含页码与原文，组件渲染「来源原文（共 N 处）」 |
| 6 | 与方案的一处偏差 | 主动改进 | `parse_status` 用 `String(16)` 而非 MySQL `ENUM`。理由：新增状态不需要 `ALTER TABLE`，演进成本更低，语义由 Python 侧的 `ParseStatus` 常量保证 |
| 7 | 两个残留文件无法删除 | 环境 | `scripts/_check_p1.py`、`scripts/_debug_parse.py` 与 `apps/web/dist*/` 被宿主程序锁定，删除与移动均被拒（WinError 5）。已加入 `.gitignore`，不影响仓库整洁 |
| 8 | `npm audit` 报 2 个漏洞 | 依赖 | 来自 Vite 5 的传递依赖，仅影响开发服务器，不进生产包 |

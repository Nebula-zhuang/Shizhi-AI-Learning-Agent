## 三、实施前说明的冲突与取舍（已按最小改动方案执行）

### 冲突 1：`/api/health` 的组件集合被 P0 测试写死为精确相等

```python
assert names == {"llm", "mysql", "chroma"}   # 原写法
```

P3 要把 embedding 加进健康检查（它是 RAG 的前置依赖，用户需要一眼看到），
这条断言必然失败。

**处理**：加入组件，断言放宽为 `{"llm","mysql","chroma"} <= names`。
放宽的方向是"允许新增"，不会掩盖 P0 组件的缺失 —— 原有的三个组件仍然被强制要求存在。

> 这个断言本身写得过严：健康检查本来就要随依赖增加而扩展，
> 而 `==` 把"允许新增"和"组件缺失"混为一谈了。

### 冲突 2：P0 的 `POST /api/chat` 是直连 LLM、不带检索

**处理**：不改它。新增独立的 `POST /api/rag/ask`，两个能力并存：
`/api/chat` 用于验证流式通道，`/api/rag/ask` 用于检索增强问答。

### 取舍 3：新增了第三个同构执行器

已有 `ingest_runner`（P1）、`verify_runner`（P2），索引需要同样的异步能力。

**处理**：新增 `index_runner`（同构、独立信号量），不动前两个。

> ⚠️ **这是第三个了，需要记账**：P4 若再出现同类需求，应当抽象成通用执行器。
> 现在不动是因为抽象必然要改两个已验收模块，而收益只是一个文件。

### 取舍 4：不做"上传即自动索引"

**处理**：索引做成独立接口，不改 P1 的摄取流水线。三个理由：
① 换 embedding 模型后必须能独立重建索引；② 未配 Key 时上传不受任何影响；
③ 不触碰经过 26 项冒烟验证的 `ingest_pipeline`。

## 四、关键实现细节

### 4.1 Embedding provider 抽象

```
EmbeddingProvider (ABC)
  ├─ APIEmbeddingProvider    OpenAI 兼容 /embeddings（默认阿里云百炼）
  └─ MockEmbeddingProvider   本地确定性向量，零网络
```

**批量 / 截断 / 重试 / 分批的编排全部放在基类**，子类只实现 `_embed_batch()`。
所以这套逻辑只写一遍，mock 与真实实现共用，测试也只覆盖一份。

| 机制 | 做法 |
|---|---|
| 批量 | 按 `EMBEDDING_BATCH_SIZE`（默认 10，百炼 v3 上限）切分，**串行**避免触发 QPS 限流 |
| 截断 | 单条超 `EMBEDDING_MAX_CHARS` 先截断 —— 超长请求会返回 400，截断比失败实用 |
| 重试 | 仅对超时 / 5xx / 429 重试；**4xx 不重试**（请求本身有问题，重试不会变好） |
| 空文本 | 替换为占位符，保证"输入 N 条一定拿到 N 条向量" |
| **顺序** | **按返回体的 `index` 重排** —— 不少供应商返回顺序与输入顺序不一致，不重排会把向量与文本错配，而这类错误检索时完全不报错，只会静默给出错误答案 |
| 维度 | 与 `EMBEDDING_DIM` 不符 → 明确报 `dim_mismatch`，不静默写入 |

错误码 6 种，各自对应用户可理解的处置：`not_configured`(409) / `unsupported`(409) /
`timeout`(503) / `http_error`(503) / `parse_error`(502) / `dim_mismatch`(500) / `empty`(502)。

**为什么 mock 用字符 unigram 而不是二元组**（实测选出来的）：

| 查询 | 相关块距离 | 无关块距离 |
|---|---|---|
| 二元组 | 0.874 | 1.000 |
| **单字符** | **0.463** | **0.954** |

二元组太稀疏，连相关块的距离都逼近 1.0，会被 `RAG_MAX_DISTANCE=0.85` 全部滤掉 ——
于是"距离门槛"相关的逻辑在 mock 下根本无法验证。单字符的分布与真实 embedding 行为接近，
因此门槛逻辑在 mock 模式下也是可测、可信的。

### 4.2 向量索引

- id = `doc{document_id}:chunk{chunk_index}` —— 可推导、稳定、幂等；
- **重建语义**：写入前先 `delete_document`。不清的话，换模型后同一份资料会同时存在
  两套语义空间的向量，排序混杂两种度量，而且**完全不报错**；
- **元数据 8 个字段**：`document_id` / `chunk_index` / `page_start` / `page_end` /
  `block_type` / `heading_path` / `file_name` / `char_count`。
  `heading_path` 必须序列化成字符串 —— Chroma 的 metadata 只接受标量，直接塞 list 会抛异常；
- **索引状态不落库**，以 Chroma 为准（`document_chunk_indexes` 对比实际块数），
  这样不存在"库里的状态与向量库不一致"这种经典问题。

### 4.3 最小 RAG

```
embed(question) → chroma.query(top_k, where) → 距离门槛过滤 → 拼带编号的上下文
              → DeepSeek 生成 → 答案 + 来源
```

**距离门槛（`RAG_MAX_DISTANCE`，默认 0.85）不是可选项。**
Top-K 永远会返回 K 条 —— 哪怕资料里根本没有相关内容。没有门槛的话，
问一个资料外的问题也会检索出 K 条无关片段，模型只能硬编答案。
有了门槛，无关片段被丢掉、上下文为空，此时**直接短路，连模型都不调用**。

**来源片段带编号**（`[1] [2]`），提示词要求模型在结论后标编号 ——
于是答案里的每个说法都能回查到具体哪份资料的第几页。

**被丢弃的片段也会返回**，并带上原因（`相似度不足（距离 0.925 > 门槛 0.85）`），
让用户看到"检索到了什么、为什么没用上"，而不是对着空来源发呆。

**提示词的三条硬性规则**（与 P1/P2 的引用优先级约定完全一致）：
① 只用片段内容作答；② 资料不足时必须明说「这部分不在你的资料中」；
③ 每处结论标出来源编号。

## 七、本阶段修掉的问题

### 问题 1：P0 冒烟脚本把生产向量集合的维度钉死了（严重）

**现象**：索引真实资料时报
`Collection expecting embedding with dimension of 4, got 1024`。

**根因**：`scripts/smoke_test.py` 的 Chroma 读写冒烟用 **4 维假向量**
（`[0.1, 0.2, 0.3, 0.4]`）写入了**生产集合** `learning_buddy_chunks`。
而 **Chroma 的集合维度在第一次写入时就固定**，之后即使把数据全部删光也无法改变 ——
所以那个集合被永久钉死在 4 维（实测 `count=0` 但维度仍是 4）。

这个缺陷从 P0 起就存在，但直到 P3 引入真实 embedding 才显形。

**修复（两处）**：
1. `scripts/smoke_test.py` 的探针改写**独立集合** `learning_buddy_smoke_probe`，
   并写明原因 —— 探针数据永不接触生产集合；
2. `VectorStore.enforce_dimension()`：写入前检查集合记录的维度，
   不符则**自动重建集合**（向量可由原文块完全重建，不存在数据丢失）；
   对"有数据但没记录维度"的旧集合，则在写入报错后重建并重试一次。

生产集合已自动修复为 1024 维，真实索引恢复正常。

> **教训**：冒烟测试写生产数据存储是个隐患。测试要用独立命名空间，
> 尤其当底层有"不可逆的一次性配置"（如 Chroma 的集合维度）时。

### 问题 2：健康检查断言写得过严

见 §3 冲突 1。已放宽为允许新增。

### 问题 3：测试夹具的 `file_hash` 与集合命名

- P3 的夹具沿用 P2 的做法（建数据前清理同 hash 残留），避免偶发失败；
- 新增约定：**Chroma 集合名不能以下划线开头**（必须是 3-512 个
  `[a-zA-Z0-9._-]` 且首尾为字母数字）。测试集合名定为 `lb-test-vectors`。

## 2. `RAG_MAX_DISTANCE` 已按真实距离分布校准：0.85 → **0.40**

新增 `scripts/calibrate_rag.py`（可复用；`--auto-questions` 会用资料自身的知识点标题当查询）。
在两份语料上实测：

| 语料 | 资料内问题·最近距离 | 资料外问题·最近距离 |
|---|---|---|
| 9 块的课程讲义 | 0.145 / 0.178 / **0.261** | **0.577** / 0.596 / 0.642 |
| 120 块的真实论文 | 0.226 / 0.246 / **0.286** | **0.415** / 0.546 / 0.568 |

合起来：**资料内最大 0.286，资料外最小 0.415**。取 0.40。

原有的 0.85 严重过松，会让大量无关片段进入上下文。
**取值刻意偏向"宁可多留一条，也不要误杀相关内容"**：误杀会让用户问一个资料里
确实有的问题却被告知"不在你的资料中"（可见的坏体验），
而多留一条无关片段还有提示词里"只依据片段作答"那条规则兜着。

**校准后 7/7 判定正确**：4 条资料内全部命中、4 条资料外全部被挡掉（含 1 条边界情形）。
校准依据与"换模型需重测"的提示都写进了 `config.py` 与 `.env.example`。

## 3. 真实验证又暴露并修掉的 3 个问题

### 问题 1：集合的维度检查抓不到"换了向量模型"

**维度相同不代表语义空间相同。** 切换 embedding 模型（或像这次从 mock 换成真实模型）时，
维度可能都是 1024，维度检查放行，而集合里**新旧两套语义空间混杂** ——
检索时距离完全不可比、排序毫无意义，**而且不会报任何错**。

**修复**：给集合加"指纹" `provider:model:dim`，随维度一起记录并比对，不符则重建集合。
早于指纹机制创建的集合会在下次索引时自动补录。

> 补录用的是 chromadb 的 `modify`，实测有个坑：**它是整体替换 metadata，不是合并**，
> 且带上 `hnsw:space` 会被拒（"Changing the distance function … not supported"）。
> 好在实测确认了：**丢掉 metadata 里的 `hnsw:space` 不影响距离函数** ——
> 手工算的余弦距离与 chroma 返回值逐位一致（0.1449 == 0.1449），
> 距离函数在集合创建时就固定在内部。这一点写进了代码注释，免得后人重新踩。

### 问题 2：LLM 生成失败会把检索结果一起丢掉

**实测场景**：DeepSeek 账户余额不足（HTTP 402）时，`LLMError` 直接冒泡成 500 ——
用户问了一个**资料里确实有**的问题，却既拿不到答案、也拿不到**已经检索出来的来源**。

余额不足、限流、超时都是常规运维事件，不该让整次问答白费。

**修复**：生成失败时降级为"只返回检索结果" ——
`generation_failed=True`、`error` 给出类别化原因（余额不足 / 凭据无效 / 限流 / 超时 / 服务不可用）、
`sources` 照常返回，正文明确说明"找到了 N 条相关资料，但模型不可用"。
**刻意不编造答案**，也不丢掉已经拿到的资料。

### 问题 3：mock 向量的距离尺度与真实模型差一个量级

把门槛从 0.85 调到 0.40 后，**所有用 mock 的测试都挂了** ——
因为 mock 的相关块距离是 0.605，而真实模型只有 0.145~0.286。
根源是 P3 当初把 mock 校准到旧的 0.85 门槛上了。

这次直接按真实尺度重新校准：给 mock 向量叠一层"均匀分量偏置"
（与均匀单位向量按 `1-b : b` 混合再归一化）。

| 构造 | 相关块距离 | 无关查询最近距离 | 阈值 0.40 可用？ |
|---|---|---|---|
| 单字符，无偏置 | 0.605 | 0.890 | ✗ 相关块本身就被滤掉 |
| 单字符，**b=0.45** | **0.344** | **0.457** | ✓ |
| 真实 text-embedding-v3 | 0.145~0.286 | 0.415~0.577 | （基准） |

b 的可用区间约 0.42~0.48，取 0.45 居中。这样 mock 与真实的距离尺度可比，
**门槛逻辑在离线模式下也可测、可信**，离线基线继续 16/16 通过。

# 响应慢诊断与优化 · 「是模型的问题吗？」

> 日期：2026-09-19
> 结论：**是模型的问题，但不是"模型慢"这么简单** —— 是「三次串行调用 + 每次都用中档模型」。
> 处理：按任务类型分模型（判断类走轻量模型），端到端 **12.8s → 5.0s**，首字 **5.8s → 3.3s**。

---

## 一、先把"模型"和"链路"分开

不猜，做对照实验（`scripts/diagnose_latency.py`）。

### 模型裸延迟（不含我们的任何逻辑，同一把 Key、同一网关）

| 请求 | 中位耗时 | 输出 |
|---|---|---|
| 回一个词 | **544 ms** | 1 字 |
| 一句话 | **1244 ms** | ~100 字 |
| 一段话 | **3004 ms** | ~281 字 |

**关键规律：耗时基本与输出长度成正比。** 模型的固定往返只有几百毫秒，
剩下的全是"一个字一个字吐"的时间。

### 我们自己的链路（优化前）

| 阶段 | 耗时 | 占端到端 |
|---|---|---|
| 生成教学内容 | 6385 ms | 51% |
| **评估作答** | **4243 ms** | 33% |
| **决策下一动作** | **1700 ms** | 13% |
| RAG 检索 | 436 ms | 3%（已并发隐藏） |
| 数据库读写 | 28 ms | 0.2% |
| **合计** | **12815 ms** | 三次 LLM 占 **96%** |

**所以答案很清楚**：96% 的时间在等模型。我们自己写的代码一共只花了不到半秒。

但这不是"模型不行"，而是两件事叠加：

1. **三次串行调用**：评估 → 决策 → 生成，一步等一步。
2. **每一次都用中档模型**（qwen-plus），哪怕其中两步只是"判断题"。

---

## 二、同一把 Key 下的模型对比

| 模型 | 一句话 | 判断类任务 |
|---|---|---|
| qwen-plus（原用） | 1615 ms | 849 ms |
| **qwen-flash** | **470 ms** | **333 ms** |
| qwen-turbo | 519 ms | 432 ms |
| qwen3-max | 1288 ms | 833 ms |

轻量模型快 **2.5–3.4 倍**。那问题就变成了：**能不能把其中几步换过去？**

---

## 三、换之前先验质量（`scripts/ab_assessment_model.py`）

评估是教学闭环的**命门** —— 它判错，后面的"换讲法/降难度/升难度"全跟着错。
所以拿真实教材素材 + 三类回答（完整 / 含糊 / 跑偏）做了对照。

| 模型 | 平均耗时 | 与基准判定一致 |
|---|---|---|
| qwen-plus | 2650 ms | 基准 |
| qwen-flash | **1015 ms** | 6 例中 4 例 |
| qwen-turbo | **774 ms** | 6 例中 5 例 |

**初看一致率不高，但差异落在哪里才是关键**：两个不一致**全部**发生在
`vague`（答得不透）与 `not_mastered`（没答对）的边界上 ——
而这条边界连提示词自己都写着"最容易误判的一类"。

而且**轻量模型选得反而更准**：

- 原回答："进程比较重，线程比较轻，线程切换快一些"
- qwen-plus 判 → `not_mastered`（判成答错）
- qwen-flash 判 → `vague`（方向对、说了一半）

后者更符合定义。`error_type` 也基本一致（6 例对 5 例）。

**结论：判断类任务可以放心降级；教学内容生成不能。** 那里质量比速度重要得多。

## 四、改了什么

**按任务类型分模型**，一个开关控制：

| 任务 | 用什么 | 为什么 |
|---|---|---|
| 评估作答 | **轻量模型** | 判断题，输出短、模式固定 |
| 决策下一动作 | **轻量模型** | 同上 |
| 生成教学内容 | 主模型 | 这是学习者的"老师"，质量优先 |

实现：

- `LLM_MODEL_FAST` 配置项（`.env`）。**留空即退回单模型，行为与接入前完全一致** ——
  这是一个可开关的优化，不是新的必要条件。
- `app/core/llm.py` 新增 `fast_llm_gateway`（未配置时为 `None`，调用方回落主网关）。
- `runtime.py` 里评估与决策走 `self.llm_fast`，生成仍走 `self.llm`。

### 一个必须处理的测试安全点

测试常用 monkeypatch 模块级 `llm_gateway` 来避免真实调用。
如果判断类任务绕过这个打桩去打真实网关，**测试会变慢、不稳定，而且是真的在花钱**。

所以 `_pick_fast_gateway` 有三条规则（从紧到松）：

1. 调用方显式传了 `llm` → 两处都用它
2. 模块级 `llm_gateway` 被替换过 → 两处都用替换后的
3. 否则用 `fast_llm_gateway`

**验证**：全量测试 128 秒（与接入前相当）→ 说明没有真实调用泄漏。

## 五、效果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| **端到端（作答轮）** | **12.8 s** | **5.0 s** | **−61%** |
| **第一个字出现** | **5.8 s** | **3.3 s** | **−2.5 s** |
| 评估作答 | 4243 ms | **1627 ms** | −62% |
| 决策下一动作 | 1700 ms | **695 ms** | −59% |
| RAG 检索 | 436 ms | 453 ms | 已并发隐藏 |

> 说明：生成内容那一步（2901 ms）**不属于本次优化的功劳** ——
> 它的耗时随输出长度变化很大，两次测量的动作不同（probe/explain/rephrase
> vs easier/easier），不能直接对比。评估与决策两项是同一任务同一提示词，可比。

### 现在的耗时构成（作答轮 ≈ 5.0 s）

```
0 ms      阶段：正在看你的回答…
           ├─ 评估作答  1627 ms  ← 轻量模型
           │  └ 同时并发：RAG 检索 453 ms（被完全遮住）
1900 ms   阶段：正在想下一步怎么教…
           ├─ 决策      695 ms   ← 轻量模型
2977 ms   阶段：正在组织讲解…
3327 ms   ✎ 正文开始逐字出现  ← 学习者从这一刻开始读
5035 ms   ✔ 完成
```

## 六、还能不能更快

| 手段 | 预期收益 | 代价 |
|---|---|---|
| **换更轻的模型**（qwen-turbo 再快 ~1.2×） | 评估 −0.2s、决策 −0.1s | 边际收益已经不大 |
| **缩短提问说明的输出** | 生成那步能省 1–2 s | 要牺牲你要求的"问什么/要答到/怎么答"格式 |
| **砍掉决策调用** | −0.7 s | 已论证否决：会让"阈值不可绕过"只被验证一半 |
| **合并决策与生成** | −0.7 s | 已论证否决：会破坏"内容一定对应最终生效动作"的保证 |
| **语义缓存**（同一知识点重复问） | 首次不变，复访 −90% | 需要引入缓存层，有失效正确性问题 |

**我的判断：到这一步性价比的拐点已经到了。** 剩下的 5 秒里，
2.9 秒是"把一段教学内容一个字一个字写出来"，这是本质成本 ——
除非缩短内容，否则降不下来。而缩短内容与你要的提问质量直接冲突。

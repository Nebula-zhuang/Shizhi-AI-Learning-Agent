## 二、需要先说明的 4 点（含最小改动方案）

### 冲突 1：`/api/health` 的组件集合被 P0 测试写死为「精确相等」

```python
# tests/test_p0_baseline.py
names = {c["name"] for c in body["components"]}
assert names == {"llm", "mysql", "chroma"}      # ← 精确相等
```

P3 想让健康检查反映 embedding 是否就绪（这是 P3 的核心外部依赖，用户需要一眼看到）。
加一个 `embedding` 组件后这条断言必然失败。

**最小改动方案**：加入组件 + 把断言从 `==` 放宽为 `⊇`（P0 的三个组件仍然必须存在）。
一行改动，且断言放松的方向是"允许新增"，不会掩盖 P0 组件的缺失。

> 这个断言的写法本身过于严格 —— 健康检查本来就是要随依赖增加而扩展的。
> 但我不擅自大改 P0 的测试意图，只做允许性放宽。

### 冲突 2：P0 的 `POST /api/chat` 是「直连 LLM、不带检索」

它是 P0 的验收项（含 SSE 流式），**不能改** —— 改了就破坏了 P0 的语义。

**最小改动方案**：新增独立的 `POST /api/rag/ask`。两个能力并存且职责清晰：
- `/api/chat` —— 直连网关，用于验证流式通道；
- `/api/rag/ask` —— 检索增强问答，带来源。

### 取舍 3：这是第三个同构执行器

已有 `ingest_runner`（P1）、`verify_runner`（P2）。索引一份 44 页资料要分批调用
embedding API（约 10 批），同步接口会让用户干等十几秒，需要异步 + 进度查询。

**最小改动方案**：新增 `index_runner`，与现有两个**同构但独立**（独立信号量、独立上限）。
不改前两个已验收的执行器。

> ⚠️ 这是**第三个**同构执行器了。三个还勉强能接受，**如果 P4 再出现第四个，就应当
> 抽象成通用执行器**。现在不动是因为：抽象必然要改动两个已验收的模块，而收益只是一个文件。
> 这一点写在这里，作为 P4 的待办，而不是现在就做。

### 取舍 4：不做「上传即自动索引」

**最小改动方案**：索引做成独立接口，不改 P1 的摄取流水线。

三个理由：
1. **换 embedding 模型后必须能独立重建索引** —— 这是必然发生的需求，独立接口天然支持；
2. **未配 Key 时上传不受任何影响** —— P1 的功能完全不被 P3 的前置条件绑架；
3. 不触碰 P1 的 `ingest_pipeline`（它经过 26 项冒烟测试验证），风险最低。

## 三、Embedding provider 抽象

```
app/rag/embedding.py

  EmbeddingError(code)                 ← not_configured / timeout / http_error
                                         / parse_error / dim_mismatch / empty
  class EmbeddingProvider(ABC)
      available -> bool
      dim -> int
      model -> str
      async embed(texts) -> EmbeddingResult
  class APIEmbeddingProvider            ← OpenAI 兼容 /embeddings
  class MockEmbeddingProvider           ← 确定性向量（hash 派生），零网络
  get_embedder() -> EmbeddingProvider   ← 按 settings.embedding_provider 选择
```

### 为什么要有 MockEmbeddingProvider

和学习 P1 的 `chat_json` mock 同样的理由：**整条 RAG 链路要能离线回归、零 API 消耗**。
mock 向量由文本 hash 确定性地派生 —— 同样文本永远得到同样的向量，
因此"相似文本距离更近"这类断言在 mock 下也成立（用字符重合度构造），测试才有意义。

### 批量处理

- `EMBEDDING_BATCH_SIZE` 默认 **10**（DashScope text-embedding-v3 的单请求上限）；
- 分批串行调用，批间不并发（避免触发供应商限流）；
- 单条文本超过 `EMBEDDING_MAX_CHARS`（默认 2000 字）先截断 —— 超长会导致 400；
- 任一批失败 → 整体失败并给出**是哪一批**失败，便于定位；
- 返回数量与输入数量不一致 → 判 `dim_mismatch` 类错误（说明返回体不可信）。

### 错误处理

| code | 含义 | 处置 |
|---|---|---|
| `not_configured` | 未配 Key | 索引/问答接口返回 409 + 明确提示去配 Key |
| `timeout` | 超时 | 503，提示重试 |
| `http_error` | 非 2xx | 503，带状态码与响应片段 |
| `parse_error` | 返回体结构异常 | 502 |
| `dim_mismatch` | 维度与 `EMBEDDING_DIM` 不符 | 500 —— 这是配置错误，必须让人看见 |
| `empty` | 返回空向量 | 502 |

## 四、向量索引

### 4.1 写入

`VectorStore` 新增 `query()` 与 `delete_document()`（在 P0 已有封装上追加，不改既有方法）。

- **id**：`doc{document_id}:chunk{chunk_index}` —— 稳定、可推导、天然幂等；
- **document**：chunk 原文；
- **embedding**：云端返回的向量；
- **metadata**（检索结果要用的全部信息）：

| key | 说明 |
|---|---|
| `document_id` | 用于 where 过滤 |
| `chunk_index` | 回链到 P1 的块 |
| `page_start` / `page_end` | 页码，用户看到的"第 X 页" |
| `heading_path` | 章节面包屑（JSON 字符串，Chroma 只接受标量） |
| `block_type` | text / table / figure |
| `file_name` | 答案里标注来源文档 |
| `char_count` | 便于排查异常块 |

> Chroma 的 metadata 只支持标量，`heading_path` 序列化成字符串存，读出来再解析。
> 这是必须记下的坑：直接塞 list 会抛异常。

### 4.2 索引状态

**不新增数据表。** Chroma 自己就是索引状态的真相来源 ——
用 `collection.get(where={"document_id": id})` 统计已索引块数，与 `documents.chunk_count` 对比。

好处：不存在"库里的状态与向量库不一致"这种经典问题。代价是查询稍慢（可接受，一次统计）。

### 4.3 幂等与重建

同一 `document_id` 重复索引时，先 `delete(where={"document_id": id})` 再写入 ——
保证不会残留旧模型产生的向量。**这是换 embedding 模型后必须的行为。**

## 五、最小 RAG

```
用户问题
  → embed(question)                      Query Embedding
  → chroma.query(top_k, where=文档过滤)   Top-K 检索（余弦距离）
  → 按相似度降序组装上下文（带编号 + 页码 + 文档名）
  → DeepSeek 生成回答
  → 返回 { answer, sources[], usage }
```

### 引用约定（沿用 P1/P2 已确立的优先级）

**用户资料 > 模型通识。** 提示词里写死三条规则：

1. 只依据提供的资料片段回答，不要引入资料之外的知识；
2. 资料不足以回答时，**必须明说"这部分不在你的资料中"**，再补充通识（并标注）；
3. 引用时标出片段编号，便于用户回查。

这三条不是摆设 —— 它正是这个项目和"套壳 ChatGPT"的分界线，
且与 P1 知识点抽取、P2 校验的引用优先级约定**完全一致**。

### 检索参数

| 配置 | 默认 | 说明 |
|---|---|---|
| `RAG_TOP_K` | 5 | 返回片段数 |
| `RAG_MAX_CONTEXT_CHARS` | 6000 | 拼接上下文的总长度上限，超出按相似度截断 |
| `RAG_MAX_DISTANCE` | 0.85 | 余弦距离上限，超过视为"不相关"直接丢弃 |
| `RAG_TEMPERATURE` | 0.2 | 事实问答要稳，不要发散 |

`RAG_MAX_DISTANCE` 这一条很关键：**Top-K 永远会返回 K 条**，哪怕资料里根本没有相关内容。
没有距离门槛的话，问一个资料外的问题也会检索出 5 条无关片段，然后模型硬编一个答案。

# P2 实施方案 · 知识点关系构建 · 可信度校验 · 联网核验 · 知识图谱

> 前置：P1 已验收通过（80 项后端测试、26 项端到端冒烟、真实 DeepSeek 实测 19 个知识点）
> 原则：**增量开发**。不重构、不重写 P0/P1 已验收的功能。
> 决策（用户已定）：联网检索用 **Tavily**；**同时**实现最小可用的知识图谱前端可视化。

## 一、先说明：P2 发现的 3 个架构问题与最小修改方案

### 问题 1：`ingest_runner` 是摄取专用的，校验任务无法复用

`app/services/ingest_runner.py` 是模块级单例：一个全局信号量 + 写死调用 `run_pipeline`。
可信度校验需要同样的能力（异步投递、并发限流、优雅关闭），但：

- 直接复用会把两类任务塞进同一个并发池 —— 上传一份 50 页 PDF 时，校验任务会被它挤住；
- 改造 `ingest_runner` 让它接受任意协程，属于**修改 P1 已验收代码**，违反增量原则。

**最小修改方案**：新建 `app/services/verify_runner.py`，与 `ingest_runner` **同构但独立**
（独立信号量、独立任务集、独立上限）。约 40 行，零 P1 改动，两类任务互不干扰。

> 这是有意接受的少量重复。抽象出通用执行器虽是"更漂亮"的做法，但会动到 P1 的稳定代码，
> 收益不抵风险。等第三个同类需求出现时再抽象。

### 问题 2：文档级的「校验进度」无处存放

校验结果必须持久化（要可追溯），但校验**进度**是瞬时状态。

**最小修改方案**：
- **结果**落 `knowledge_checks` 表（append-only，一条记录一次校验，保留全部历史）；
- **进度**放 `verify_runner` 的内存态，通过 `GET /api/documents/{id}/verify/status` 暴露，
  同时用 DB 统计出「已校验 / 总数」作为兜底。

不新增 `documents` 表字段。重启后进度条会丢，但**已产生的校验结果一条都不会丢** —— 这是可接受的取舍。

### 问题 3：`verify_status` 到底算不算「覆盖 P1 抽取结果」

`knowledge_points.verify_status` 在 P1 就存在，字段注释原文写着「P2 使用」，
默认值 `unverified`，且已出现在 `KnowledgePointSummary` DTO 里。**它是 P1 为本阶段预留的位。**

**约定（写进测试断言）**：P2 只允许写这一个字段。P1 的抽取产物 ——
`title` / `title_norm` / `summary` / `details` / `key_points` / `difficulty` / `importance` /
`confidence` / `tags` / `heading_path` / `source_chunk_indexes` / `source_pages` / `order_index`
—— **一律只读，P2 绝不修改**。校验发现的问题写进 `knowledge_checks`，不改原始数据。

## 三、数据模型

### 3.1 `knowledge_relations`（新增）

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| document_id | BIGINT FK→documents CASCADE | 便于按文档整体查询与级联删除 |
| from_kp_id | BIGINT FK→knowledge_points CASCADE | 关系起点 |
| to_kp_id | BIGINT FK→knowledge_points CASCADE | 关系终点 |
| relation_type | VARCHAR(24) | `prerequisite` / `related` / `contains` |
| confidence | NUMERIC(3,2) | 该条关系的置信度 |
| source | VARCHAR(24) | **构建依据**（见第四节），不允许为空 |
| evidence | VARCHAR(512) | 人类可读的依据说明，如「同在 3.2 节下」 |
| created_at | DATETIME | |

约束：`UNIQUE(from_kp_id, to_kp_id, relation_type)`；索引 `document_id` / `from_kp_id` / `to_kp_id`。

**关于 `contains` 与 `belongs_to`**：二者是同一关系的正反视角。
**数据库只存一个方向**（`contains`：父→子），避免同一条边存两份导致图里出现重影。
`belongs_to` 由接口层派生（边的 `inverse_type` 字段 + UI 反向标签「属于」）。
`prerequisite` 有向（前置→后继）；`related` 无向，只存一条，查询时双向匹配。

### 3.2 `knowledge_checks`（新增，append-only）

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| kp_id | BIGINT FK→knowledge_points CASCADE | |
| document_id | BIGINT FK→documents CASCADE | |
| check_type | VARCHAR(16) | `rule` / `model` / `web` —— **三层严格分开** |
| verdict | VARCHAR(16) | `passed` / `suspicious` / `unsupported` / `skipped` / `error` |
| confidence | NUMERIC(3,2) | 该次校验给出的置信度 |
| reason | VARCHAR(512) | 结论理由 |
| evidence | JSON | 结构化证据（规则命中项 / 模型理由 / 联网命中的标题摘要） |
| source_urls | JSON | 联网核验的出处链接（仅 `web` 层有值） |
| engine | VARCHAR(32) | `rule-v1` / `deepseek-chat` / `tavily` —— 可追溯是谁下的结论 |
| created_at | DATETIME | |

索引：`(kp_id, check_type)`、`document_id`。

**为什么要单独一张表而不是给 `knowledge_points` 加列**：这直接回应「不要覆盖 P1 原始抽取结果，
保留可追溯性」。校验是**可重复发生的事件**，同一知识点可能被校验多次（换模型、换提示词、
补配了 Tavily Key 后重跑），如果写成列，历史必然被覆盖；写成行则完整留痕。

## 四、关系构建：每一种关系都必须有依据

**硬性要求：不允许随机连边。** 每条边都必须能回答「你凭什么认为它们有关系」。

| 关系 | 构建依据 | 置信度 | evidence 示例 |
|---|---|---|---|
| `contains` | 两知识点的 `heading_path` 前缀包含关系（父的路径是子的前缀） | 0.90 | `「3.2 进程的状态」是「3.2.1 就绪状态」的上级章节` |
| `contains` | 无章节层级时，退化为 `title` 包含关系（A 的标题是 B 标题的子串且 A 更短） | 0.70 | `「信号量机制」包含「信号量」` |
| `related` | 两知识点共享至少一个 `source_chunk_indexes`（同一段原文抽出） | 0.60 + 0.1×重叠数（上限 0.85） | `同出自块 #3` |
| `related` | `heading_path` 完全相同（同一小节下的同级考点） | 0.55 | `同在「3.6 死锁」小节下` |
| `prerequisite` | **顺序 + 章节双重信号**：A 的 `order_index` 严格早于 B，且 `heading_path` 层级 ≤ B 或为 B 的前缀 | 0.50 | `「进程的定义」出现在「进程与线程的区别」之前，且为同章前置小节` |

**明确不做的连边方式**：不按 title 字符串相似度乱连、不按 order_index 相邻就连（相邻 ≠ 前置，
同小节下的相邻考点是"相关"而非"前置"）、不做全连接。

**幂等**：重建时先清空该文档的旧边再写新的，与 P1 的 `purge_derived` 思路一致。

**可选 LLM 细化（默认关闭）**：`prerequisite` 的方向有时规则判不准。
留一个 `relation_llm_refine` 开关，开时对规则产出的 `prerequisite` 候选做一次模型确认，
模型只能**保留或删除**候选边、不能新增边 —— 保证"无依据不连边"这条底线不被模型突破。

## 五、可信度校验：三层严格分离

呼应技术方案里的 L1 → L2 → L3 设计，层层过滤，越往后越贵：

### L1 规则校验（确定性，零成本，所有知识点都跑）

| 检查项 | 判定 |
|---|---|
| 溯源完整性 | `source_chunk_indexes` 非空且都能查到对应 chunk → 否则 `unsupported` |
| 页码有效性 | `source_pages` 落在文档真实页码范围内 |
| 标题规范 | 长度 ≤20、非空、不含句子标点 |
| 摘要长度 | ≤60 字 |
| 通识外溢 | `details` 里出现「一般来说」「通常」「此外」等引导词且该句在原文中找不到依据 → 记 `suspicious`（提示可能混入模型通识） |
| 关系依据 | 该知识点参与的所有边都必须有 `source` 与 `evidence` |

### L2 模型自评（LLM，只对「值得问」的知识点跑）

触发条件（闸门）：`importance >= 4`，或 L1 判为 `suspicious`。
让模型只回答一个问题：**给定原文块，这条知识点的 summary/details 是否忠实于原文？**
输出 `faithful` / `overstated` / `unsupported` + 理由。结果写 `check_type='model'`。

### L3 联网核验（Tavily，只对「L2 未通过或高重要度且可疑」的知识点跑）

**触发闸门（严格，避免浪费搜索配额）**：
1. `verify_web_enabled` 为真且 Tavily Key 已配置；
2. L2 verdict ∈ {`overstated`, `unsupported`}，**或** L1 判定为「可能混入通识」；
3. **常识性稳定知识点一律跳过** —— 判定方式：`difficulty <= 2` 且 `importance <= 3` 且
   L1/L2 均未报警（这类知识点联网搜索纯属浪费，且更容易引入噪声）；
4. 单文档联网核验次数上限 `verify_web_max_per_document`（默认 8）。

**结果**：把 Tavily 返回的标题/摘要/URL 存进 `knowledge_checks.evidence` 与 `source_urls`，
verdict 为 `passed`（找到一致证据）/ `suspicious`（证据冲突或找不到）。

### 引用优先级（沿用 P1 约定）

用户资料 > 联网证据 > 模型通识。联网证据**不得**覆盖用户资料，只能作为补充证据记进 checks；
若联网结论与用户资料冲突，verdict 记 `suspicious` 并把双方证据都留下，由用户判断。

### 最终 `verify_status` 汇总规则（写回 `knowledge_points.verify_status`）

只写这一个字段：
- 任一 L2/L3 判 `unsupported` → `conflict`
- 任一 L2/L3 判 `overstated` 或 L1 有 suspicious → `suspect`
- L3 明确找到更权威的相反说法 → `outdated`
- 全部通过且至少有一层非 rule 的校验 → `trusted`
- 其余 → `unverified`

**无 Tavily Key 时的降级**：L3 整层标 `skipped`（reason 写明「未配置 TAVILY_API_KEY」），
L1/L2 照常跑。**P1 功能完全不受影响。**

## 六、Tavily 接入：解耦设计

```
app/search/tavily_client.py     ← 纯 HTTP 客户端，不认识「知识点」这个概念
        ↑
app/services/verify_service.py  ← 业务层：决定「核验什么」「结论怎么用」
```

`tavily_client` 只暴露：`search(query, *, max_results) -> list[TavilyResult]`，
以及明确的错误类型 `SearchError(code, message)`，`code ∈ {not_configured, timeout, http_error, empty}`。
它不知道知识点、不知道数据库、不知道 `verify_status` —— 换成 Serper 只需新写一个同签名的客户端。

**约束**：
- API Key 只从 `settings.tavily_api_key`（← 环境变量 `TAVILY_API_KEY`）读取，**不硬编码**；
- 超时（默认 10s）、HTTP 错误、无结果都有明确状态码与可读信息；
- 未配置 Key 时客户端构造即抛 `not_configured`，业务层捕获后整层跳过并记 warning。

## 八、前端方案

### 不引入任何图库，用手写 SVG

- **不做图数据库**（用户明确排除），节点边全部来自一次 `GET /graph`。
- **不引 d3**。P2 的关系以 `contains`（章节层级）为主，**分层布局**（层级 = 层级深度、
  同层按 `order_index` 横排）语义最贴切，且完全确定性 —— 可测试、无随机抖动、无额外依赖。

### 组件

| 文件 | 职责 |
|---|---|
| `api/graph.ts` | 复用 P1 的 `getJson/postJson`，不重复造 HTTP 封装 |
| `features/graph/KnowledgeGraphView.tsx` | 选文档 → 拉图谱 → 组装视图 |
| `features/graph/GraphCanvas.tsx` | SVG 渲染：节点、边、关系类型标签、层级带 |
| `features/graph/NodeDetailPanel.tsx` | 节点详情：**复用 P1 的 `SourceViewer`** + 校验收据区 |
| `features/graph/useGraph.ts` | 取数 + 校验轮询 |

**对 P1 前端的改动只有 2 处，均为增量**：
1. `App.tsx` 增加第三个视图 `'graph'`（`type View` 加一个联合成员 + 一个 tab 按钮）；
2. `SourceViewer.tsx` 增加一个可选的「校验收据」区块（新增 props，默认不传则行为不变，P1 调用点零改动）。

**衔接要求**：点击图节点 → 右侧详情面板展示 P1 的知识点详情与「来源原文（共 N 处）」，
与 P1 资料库里的溯源体验完全一致。

## 二、动手前发现的两处与需求假设不符

这两点在 `docs/09-P4-实施方案.md` §1 已先说明，此处复核实际处理。

### 不符 1：那四张表**都不存在**

需求写的是「优先复用现有 `learner_kp_states`、`sessions`、`messages`、`answer_evaluations` 等表」。
实际数据库当时只有 7 张表：

```
alembic_version  app_meta  chunks  documents
knowledge_checks  knowledge_points  knowledge_relations
```

`docs/01-技术方案-v1.md` 的 ER 设计里有这四张表，但 P0 的迁移文档明确写明
「`users` —— P1 无登录、无消费者，建了就是空表（P5 再建）」，学习相关的表同理推迟到了 P4。

**处理**：用 **Alembic 0004** 新建四张表（符合"如需改表使用 Alembic"），
字段按 `docs/01` 的 ER 设计 + 需求点名要求的字段名。未重复造表 ——
`documents` / `knowledge_points` / `chunks` 全部复用。

### 不符 2：五个工具里**只有 `retrieve_knowledge` 存在**

| 工具 | 实际状态 | 处理 |
|---|---|---|
| `retrieve_knowledge` | P3 已有检索能力 | **包装复用**（`rag_service.retrieve_knowledge` 组合 P3 的 `embed` + `retrieve`，排序/门槛/元数据全部复用） |
| `get_learner_state` / `update_learning_state` | 不存在 | 新建（`learner_service`） |
| `evaluate_answer` / `generate_question` | 不存在 | 新建（`assessment_service`） |

`app/agent/` 当时只有 `__init__.py` 占位（P0 留的骨架），
所以「现有的 Lightweight Agent Runtime」是**新建**的 —— `policy.py` / `runtime.py` /
`tools/` 正好是那个占位文件里规划的内容。

### 一处取舍：`learner_id` 用字符串，不建 `users` 表

需求要求保存 `learner_id`；技术方案里是 `user_id` 外键指向 `users`。
但**用户体系属 P5**，现在建 `users` 只会得到一张没有登录入口的空表。

**处理**：`learner_id` 用 `VARCHAR(64)`，默认 `"local"`。
P5 引入用户时加一列外键并迁移即可，不返工。

## 三、数据层（Alembic 0004，四张新表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sessions` | learner_id / document_id / knowledge_point_id / status / action_count | 会话是**过程** |
| `messages` | role / content / **action_type** / **reason** / **state_snapshot** / refs | 每条助手消息留下决策证据 |
| `answer_evaluations` | correct / score / **confidence** / level / error_type / missing_points / misunderstood_points / feedback | 教学决策的燃料 |
| `learner_kp_states` | mastery / attempt_count / correct_count / **consecutive_correct** / **consecutive_wrong** / last_error_type / status | 学习状态是**长期记忆** |

两个刻意的设计：

1. **`messages` 存 `reason` 与 `state_snapshot`。**
   P4 要证明「Agent 会根据学习状态改变教学策略」。只存一句"讲了一句话"是证明不了的 ——
   必须能回放出**当时状态是什么、为什么选了这个动作**。

2. **`mastery` 用 `DECIMAL(4,3)` 而不是 `(3,2)`。**
   增量可能只有 0.004，`(3,2)` 会把它四舍五入成 0，看起来像"状态没更新"。

## 四、Policy：阈值唯一权威

### 4.1 规则与优先级

**顺序本身就是设计**，有测试守着：

| # | 条件 | 动作 | 可被 LLM 覆盖 |
|---|---|---|---|
| 1 | 掌握度达标 | `summarize` | ❌ 强制 |
| 2 | 连续答错 3 次 | `easier` | ❌ 强制 |
| 3 | 连续答错 2 次 | `rephrase` | ❌ 强制 |
| 4 | 答对但浅 | `probe` | ✅ 推荐（自由区） |
| 5 | 连续答对 2 次 | `harder` | ❌ 强制 |
| 6 | 答错且基础薄弱 | `explain` | ✅ 推荐（自由区） |
| 7 | 初次接触 | `explain` | ❌ 强制 |
| 8 | 其它 | `probe` | ✅ 推荐（自由区） |

两处刻意的排序：
- **规则 4 排在规则 5 前**：连续答对但每次都很浅时，加难度只会更懵，先问透（`test_shallow_correct_beats_correct_streak`）；
- **规则 2 排在规则 3 前**：连错 3 次同时满足"连错 2 次"，但换讲法已证明无效，该降难度（`test_easier_beats_rephrase_at_three_wrong`）。

### 4.2 mastery 增量公式

```
答对：mastery += 0.35 * score * (1 - mastery)     # 越接近掌握增益越小，渐进逼近
答错：mastery -= 0.30 * (1 - score) * mastery     # 按当前掌握程度比例回退
```

钳制在 `[0,1]`。实测约 **5–6 次高分答对**从 0 推到 0.85 阈值 ——
正好够演示一个完整闭环，不会长得让人失去耐心（有测试断言步数在 3–10 之间）。

### 4.3 阈值不可被 LLM 绕过

```
Policy.decide()  →  命中阈值规则则「锁定」动作，否则给出允许集合
        ↓
LLM 提案 { action, knowledge_point_id, reason, confidence }
        ↓
Policy.validate()  →  越权一律丢弃，回退到 Policy 的动作
```

`validate` 拒绝五种情况：非 JSON、未定义动作、不在允许集合、kp_id 越权、confidence 越界。
被拒时**整个提案作废**并回退 —— Agent 的决策权只存在于 Policy 划定的空间内。

**阈值一个都不在 Prompt 里**：给模型的是"情境描述"（"学习者最近反复出错"），
不是数字。有测试逐字检查三个 Prompt 文件不含阈值数字与阈值句式
（实测抓到过一次：示例 JSON 里的 `0.85` 正好等于掌握阈值）。

## 五、Tutor Runtime

### 5.1 状态机

```
LOAD_STATE → RETRIEVE → DECIDE_ACTION → EXECUTE_ACTION → WAIT_USER
                                                              ↓
                    NEXT_TURN ← UPDATE_STATE ← ASSESS ← ───────┘
```

- `POST /start` 跑前半段；`POST /answer` 跑 `ASSESS → UPDATE_STATE → NEXT_TURN`（再走一遍到 EXECUTE）
- **运行态不落库** —— 完全由 `learner_kp_states` + `messages` 推导，不存在"运行态与实际数据不一致"
- 每轮响应返回 `trace`，测试直接断言状态顺序

### 5.2 预算（硬约束）

| 计入预算（3 次/轮） | 不计入 |
|---|---|
| `retrieve_knowledge`（调 embedding + 查向量库） | `get_learner_state` / `update_learning_state`（纯本地读写） |
| `generate_question`（调 LLM） | Agent 自身的决策推理（是 Agent 的一步，不是工具） |
| `evaluate_answer`（调 LLM） | |

于是每轮调用数天然有界：开始轮 2 次、作答轮 3 次。
预算耗尽后 `RETRIEVE` 被跳过、后续调用被直接拒绝（**拒绝不算"已用"**，否则统计会自相矛盾）。

### 5.3 五条降级路径

| 环节 | 失败时 | 测试 |
|---|---|---|
| RAG 检索 | 不带资料继续 | `test_rag_no_result_still_works` |
| 决策 LLM | 用 Policy 动作 | `test_llm_timeout_degrades_gracefully` |
| 内容生成 | 兜底模板 + `degraded` 标记 | `test_content_generation_failure_uses_template` |
| 作答评估 | 启发式评估 + `engine=heuristic` | `test_assessment_timeout_falls_back_to_heuristic` |
| 状态更新 | **如实报告 `state_updated=false`** | `test_state_update_failure_is_reported_honestly` |

## 六、本阶段修掉的 3 个真实缺陷（都是真实模型才暴露的）

### 缺陷 1：`GeneratedContent` 未定义，内容生成**静默全程走兜底模板**

把 `generate_question` 的返回类型改成 dataclass 时，只加了 `__all__` 却忘了定义类本身。
`from __future__ import annotations` 让类型注解变成字符串，所以 import 不报错，
但运行时 `return GeneratedContent(...)` 抛 `NameError` → 被 ToolRunner 当成工具失败 →
**每一轮都静默回退到兜底模板**。

**为什么测试没发现**：兜底模板是"成功"的 —— 所有只断言"内容非空"的用例全都照样通过。

**修复 + 补测试**：加了三条断言"内容不是兜底产物"的用例
（`test_content_comes_from_model_in_happy_path` 等），并断言 `degraded is False`、`notes == []`。

> 教训：**兜底路径是"成功"的，所以只检查"有没有内容"发现不了兜底被误用。**
> 必须显式断言"这不是兜底产物"。

### 缺陷 2：决策 Prompt 没给知识点 id，导致 **Agent 的决策权完全失效**

`render_decision_prompt` 只传了标题与摘要，没传 id。真实模型只能**猜**，
返回了 `123`、`0` 这类数字，于是每轮都被 kp_id 越权校验拦下、回退到 Policy 的动作 ——
**护栏变成了墙**，Agent 的决策在真实模式下等于不存在。

```
[修复前] 模型提案被 Policy 拦截（knowledge_point_not_in_scope，提案 explain），回退到 explain
        （连续 9 轮全部如此）
```

**修复**：Prompt 里明确给出 `id=...` 并要求原样回填；越权校验保留（它现在测的是真问题）。
修复后真实模型的选择与理由都被正常采纳，例如：

> 「答错因审题偏差而非概念不懂，需追问引导其去掉前提做条件检验，而非继续重复讲解」

### 缺陷 3：`summarize` 被放进了自由区，**等于让 LLM 自己定义掌握阈值**

`summarize` 是"达成掌握"这个阈值的终端动作，但它出现在自由区的允许集合里，
于是真实模型在 **mastery 只有 0.60** 时就选了 summarize，把会话提前收束 ——
「达到掌握阈值才总结」这条规则形同虚设。

**修复**：`summarize` 从所有自由区集合中移除，引入 `THRESHOLD_ONLY_ACTIONS`，
它**只能由 R1（掌握度规则）产生**。新增两条测试守着
（`test_summarize_is_never_in_a_free_zone`、`test_llm_cannot_summarize_before_mastery`）。

> 这三个缺陷有一个共同点：**只有接上真实模型才会显形。**
> mock 用的假模型太"听话"，不会猜错 id、不会提前收束、不会触发工具内部的异常路径。

### 顺带修掉的：P0 基线的随机红灯

`tests/test_p0_baseline.py` 的对话测试会打**真实 LLM**，模型限流/抖动时
`status_code == 200` 变成 502 —— 我在连跑几轮真实演示之后真的踩到了。
这些用例的意图是验证接口契约（`assert body["mode"] in {"live","mock"}` 已说明作者预期两种模式），
加 autouse 夹具强制 mock。与 P2 对"测试依赖真实 LLM"的处理一致。

### 7.2 真实 DeepSeek 模式

`python scripts/p4_smoke.py --live` → **24/24 通过**

```
知识点：《进程与线程的区别》
  第 1 轮  [讲解]  规则=R7_first_contact
          理由：首次接触该知识点，掌握度为0且无作答记录，需要先建立基本概念，讲解最贴合。
  第 2 轮  [追问]  规则=R8_default              对(0.95)  mastery 0.000 → 0.332
          理由：仅作答1次，虽判定扎实但样本太少，先用追问确认理解深度，再考虑升难度。
  第 3 轮  [升难度] 规则=R5_correct_streak_2 🔒   对(0.95)  mastery 0.332 → 0.554
          理由：连续两次答对且深度达 mastered，基础已稳固，可推进到更复杂的应用场景。
  第 4 轮  [升难度] 规则=R5_correct_streak_2 🔒   对(0.95)  mastery 0.554 → 0.702
  第 5 轮  [升难度] 规则=R5_correct_streak_2 🔒   对(0.90)  mastery 0.702 → 0.796
  第 6 轮  [总结]  规则=R1_mastered 🔒           对(0.85)  mastery 0.796 → 0.857
          理由：掌握度0.86、连续5次答对，已达掌握标准；虽可补边界例子，
                但当前应优先收束要点、巩固知识结构。
```

**真实模型的决策理由是这一段的核心证据** —— 它会结合错因、作答深度、连击样本量
给出因人而异的判断，而不是每轮随机或套模板。

> 关于真实性的一点说明：live 模式下「学生」的回答由一次额外的模型调用生成
> （`simulate_student`，依据资料针对**当前这一轮的题目**作答）。
> 否则固定文本会被判"审题偏差"，mastery 永远涨不上去、走不到 summarize。
> 这个辅助只在冒烟脚本里，不属于产品代码。

## 十、与方案的偏差

| # | 偏差 | 说明 |
|---|---|---|
| 1 | 新增第 5 个接口 `/capabilities` | 让前端拿阈值而不硬编码数字 |
| 2 | `sessions` 多了一个 `knowledge_point_id` | 技术方案的 sessions 只有 document_id；P4 的会话围绕一个知识点展开 |

| 5 | `summarize` 被移出自由区 | 见 §6 缺陷 3（这是修正，不是偏差） |
| 6 | 前端只有验证页 | 按需求"不做最终 UI 美化" |

## 十一、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **未做多轮对话记忆压缩** | `messages` 全量保留，但喂给 Prompt 的只有当前轮的资料与状态。长会话（20+ 轮）后模型看不到早期问答细节。P5 若要做学习报告，需要在此基础上加摘要 |
| 2 | 降级时 `degraded` 只有一个布尔标记 | 具体原因在 `notes` 里（人读友好），但没有结构化的降级码，前端只能整块展示 |
| 3 | 状态更新失败后本轮决策仍会继续 | 用未更新的状态决策（如实反映），但当前轮的"下一动作"提示可能与学生刚看到的评估不一致。已在界面明确标注"状态未写入成功" |
| 4 | Tool 预算的 3 次是硬编码常量 | 未做成配置项。改动会改变每轮调用数，属于需要谨慎调整的参数，暂不开放 |
| 5 | embedding 未配置时 RAG 检索会降级 | 与 P3 的限制 #1 同源：`EMBEDDING_API_KEY` 仍为空，教学内容的"依据"来源为空。**不影响教学闭环本身**（已设计为无资料也能继续） |
| 6 | `retrieve_knowledge` 用的是知识点标题+摘要作查询词 | 比"用学生的上一句回答"更稳定，但对追问式的精细检索不够灵敏 |
| 7 | 未做学习报告聚合 | 技术方案里 `generate_report` 标注为"后续"。数据（`answer_evaluations` + `learner_kp_states`）已齐备，随时可做 |

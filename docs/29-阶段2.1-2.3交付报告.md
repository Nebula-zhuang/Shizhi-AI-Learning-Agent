## 2.1 实时能力触发 + Time Tool

### 先说 bug 复现（它比预想的严重）

```
用户问："今天几号？"
→ 没被识别成实时问题，走快通道
→ 模型靠记忆回答："今天是2024年6月13日"
→ 实际是 2026年9月20日，**差了两年多**
```

**这类错误比"不回答"更糟**：它答得非常自信，用户没有理由怀疑，
除非他自己知道今天几号（那他就不会问了）。

### 两个根因

**① 识别漏了。** `_RECENT_HINTS` 里有 `今年/明年/去年`，但**没有 `今天`**，
也没有 `几号 / 星期几 / 几点 / 哪一天`。所以那些问题全落在快通道里。

**② 就算识别到了，"联网"也是错的工具。**
问日期该查**本机时钟** —— 它权威、免费、瞬时。联网查日期反而引入延迟和不可靠来源。

### 修法：两层，缺一不可

**第一层：识别。** 新增 `_TIME_HINTS`，覆盖
`今天/明天/昨天/后天/前天/几号/几日/几月/星期几/礼拜几/周几/哪一天/什么日子/几点/当前时间/此刻/今年/…`
命中的问题**进 Agent 循环**。

**第二层（更关键）：预注入。**

> 只做"识别 + 进循环"是**不够的** —— 那仍然**指望模型主动去调时钟工具**，
> 而实测它就是不调、直接凭记忆答。

所以识别到时钟信号时，**在进循环之前就把真实时间放进观察里**：

```python
time_spec = tool_registry.get("current_time")
if time_spec is not None and _TIME_HINTS.search(question):
    observation.record(time_spec.name, await time_spec.handler())
```

这样模型看到的素材里就有正确日期，**想答错都难**。

这是"**不依赖模型自觉**"的思路 —— 与"硬限制写在代码里"是同一条原则。

### Time Tool 的设计

- **`counted=False`**：本地读，零外部成本、幂等、瞬时。
  让它跟联网搜索抢那 3 次配额没有道理 ——
  那会在"先问日期、再联网查别的"这种组合里无谓地吃掉一次。
- **零参数**：调用它不需要模型构造任何东西，这也是它可靠的原因之一。
- **星期几自己查表**，不用 locale —— 容器里不保证装了中文 locale。
- 素材里明确写着"**这是权威值，直接用它回答，不要凭记忆推断**"。
- 工具描述里写明"**这类问题不要用联网搜索**"。

### 实测结果

```
"今天几号？"    → 今天是2026年9月20日，星期日。   ✅（原来答 2024-06-13）
"今天星期几？"  → 星期日。                        ✅
概念问题        → 仍走快通道，无误伤               ✅
浏览器实测      → 2026 / 9月 / 20日 全部命中，无误答其他年份 ✅
```

## 2.2 图片上传 HTTP 链路

### 新增 `POST /api/study/attachments`

**刻意复用书房上传的同一套存储与摄取**（`storage.stream_to_temp` →
`validate_upload` → 去重 → `finalize_source` → `Document` → 投递摄取）：

> 一份文件不管从书房传还是从对话里传，都该落到同一个地方、走同一条处理链。
> 两套实现迟早会在"去重规则""大小限制""格式判定"上分叉。

**也刻意复用 `documents` 表，不另建 `attachments` 表**：
一个用户上传的图片**就是一份资料**，它该出现在"书房"里、也该能被检索。
另建表会让同一份文件在两处出现，然后"删了对话里的图、书房里还在"这类不一致就会冒出来。

### ⚠️ 修了一个设计缺陷：模型不可能知道图片路径

原来 `image_analysis` 的签名要模型传 `image_path`。但**那是服务端的内部信息**，
从来没有出现在对话里 —— 模型只能编一个、然后失败。

**正确分工**：工具该知道"这一轮有哪些图片"，模型只需要说"关于这张图我想知道什么"。
所以在本轮构造注册表时把附件路径**绑定**进 handler：

```python
handler = partial(image_analysis, image_paths=list(images), default_question=user_question)
```

模型看到的工具参数里**只有 `question`**。

### ⚠️ 又修了一个：`question` 不该是必填（这条差点让功能完全不通）

实测：模型调了 `image_analysis` 却**不传参数**，被我的校验拦下 → 重试 → 又拦下
→ 撞上重试上限 → 最后回一句"我看不到图"。

**15 秒里整个功能形同不存在。**

**那不是模型的错，是 schema 错了**：工具已经绑定了本轮的图，
"看一眼"这个动作本身不需要参数，模型省略它是完全合理的。

改法：`question` 改为可选，缺省时用**绑定的 `user_question`**（也就是用户真正问的话），
再退一步用一句通用提取要求。这样模型只写 `{}` 也能得到一次贴题的看图。

### ⚠️ 顺带修的 UI 缺口：被拒的调用以前是"闷掉"的

"未知工具 / 不可用 / 缺参数 / 超重试上限"这些分支原来直接 `continue`，
**不推任何事件** —— 于是"它做了什么"里什么都没有，
用户只看到回答说"我看不到图"，却不知道为什么。

现在这些分支也推 `tool_result`（`ok=False` + 原因）。
**失败也要可见**，这是"状态必须真实"那条规矩的延伸。

### 前端：四个入口，一个上传函数

| 入口 | 为什么要有 |
|---|---|
| 点 `＋` 选文件 | 常规路径 |
| **粘贴截图** | 最常用 —— 他刚截了图，不想再存一遍 |
| 拖拽文件到输入框 | 从文件夹直接拖 |
| （统一汇到 `acceptFiles`） | 避免"粘贴能传、拖拽不行"这类不一致 |

配套：附件先显示成卡片（可撤掉再发）、显示人类可读的大小（不是字节数）、
**允许"只发图不写字"**（自动补一句"帮我看看这个"）。

### 实测结果

```
匿名上传/列举      → HTTP 401 ✅
上传               → document_id=9018，is_image=True ✅
重复上传           → dedup=True，同一个 id ✅
格式校验           → .exe 被拒，报错里列出允许的格式 ✅
浏览器             → ＋ 按钮存在 ✅ / 文件选择器存在 ✅
                     塞入文件后**附件卡片出现** ✅
```

## 2.3 视觉模型

### ⚠️ 先更正上一份报告里的一个错误

我在 `docs/28` 里写的是"当前配置的模型是 DeepSeek"。**那是错的。**

实际配置是：

```
model    = qwen-plus
base_url = https://dashscope.aliyuncs.com/compatible-mode/v1   （阿里云百炼）
```

### 好消息：百炼本身就有视觉模型

实测同一个 Key 下**三个 VL 模型都能用**：

| 模型 | 结果 |
|---|---|
| `qwen-vl-max` | ✅ 读出 `fib` 与 `55` |
| `qwen-vl-plus` | ✅ |
| `qwen3-vl-plus` | ✅ |
| `qwen2.5-vl-72b-instruct` | ❌ HTTP 403 |

### 设计：视觉用**单独的模型**，不整体换掉主模型

主模型（`qwen-plus`）处理文本更便宜、更快；视觉任务只在"用户真的传了图"时发生。
整体换成 VL 模型会让每一轮纯文本对话都付 VL 的价钱。

所以加了 `vision_gateway()` —— 与项目里已有的 `llm_model_fast` 是**同一个模式**：
不新建连接池配置，只把 `llm_model` 换掉，超时/密钥/base_url 全部继承。

```bash
LLM_VISION_MODEL=qwen-vl-max
LLM_SUPPORTS_VISION=true
```

### 能力标志默认仍是 `False`

**它必须按部署显式声明。** 同一个网关地址，配的模型可能支持视觉也可能不支持；
"发过去看行不行"是不行的 —— 实测不支持时**接口不报错**，
只是回一句"我看不到图"，然后就变成一个 `ok=True` 的废结果。

所以：默认 `False`，验证可用后在 `.env` 里显式打开。`.env.example` 里是占位值。

## 场景 C：图片 → Agent → Vision LLM → 回答 ✅

```
上传 code.png（含 fib 递归函数）
带图提问："这张图里的代码在做什么？输出是什么？"

step 1: DECIDE  tool=image_analysis  ok=True     ← 真的看了图
step 2: DECIDE  tool=None                        ← 收尾

事件: {status: 2, tool_start: 1, tool_result: 1, source: 1, delta: 42, done: 1}
耗时 18.2s

图内标识符：fib ✅  递归 ✅  55 ✅
```

### 一个意料之外的强证据

浏览器验收时我用的测试图**漏掉了基础条件**：

```python
def fib(n):
    return fib(n-1)+fib(n-2)     # ← 没有 if n < 2: return n
print(fib(10))  # 55
```

模型的回答：

> 这段代码试图用递归方式计算斐波那契数列的第10项，预期输出是55。
> **但它实际运行会崩溃** —— 因为函数没有基础情况…每次调用都会无限向下递归，
> 最终触发 RecursionError。…**注释 # 55 是人为标注的"理想结果"，不是真实运行结果。**

它不只是"认出这是 fib"（那只能说明它见过类似代码），
而是**读到了图里的具体结构、发现了我没写基础条件**。

这是"它确实看了图"最有力的证据 —— 编是编不出这种细节的。

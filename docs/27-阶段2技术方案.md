方案建立在两条**实测**结论上，不是查文档得来的：

### 事实 1：Tavily 官方 MCP Server 真实可用（已跑通完整握手 + 真实搜索）

```

Authorization: Bearer <TAVILY_API_KEY>

                 protocolVersion "2025-06-18"

② tools/list  → 5 个工具
③ tools/call  → tavily_search("Java 25 virtual threads") → isError:false，返回真实结果
```

### 事实 2 ⚠️ 官方 README 与实际不一致

| | 工具名 |
|---|---|
| README / 各 MCP 目录站写的 | `tavily-search`（**连字符**） |

## A. 现有代码审查结果

### A1. `free_study.py`（阶段 1 我写的，共 540 行）

**结构**

```
StudyPlan / TurnEvent / TurnOutcome    三个数据类
quick_route()                          启发式快通道（不调模型）
decide()                               模型兜底决策
_parse_plan()                          收束模型输出
stream_turn()                          一轮的主流程
```

**问题**

| # | 问题 | 说明 |
|---|---|---|
| A1-1 | **不是 Agent，是"一次决策 + 一次生成"** | `stream_turn` 里决策只做一次：`decide()` → 按结果执行能力 → 生成。**没有"看完工具结果再决定下一步"** |
| A1-2 | **能力名硬编码在 `if` 里** | `if plan.wants_kb:` / `if plan.wants_web:` —— 加第三个能力就要改主流程 |
| A1-3 | **没有统一的 Tool 契约** | 检索直接调 `rag_service.retrieve_knowledge`，搜索直接调 `search.search`，两者入参/返回/错误处理各不相同 |
| A1-4 | **没有重试** | 联网失败只是记一条日志然后继续；没有"换个查询再试一次" |
| A1-5 | **`_render_material` 是字符串拼接** | 素材靠拼 Markdown 段落，没有结构化的"工具结果"概念 |
| A1-6 | 决策与生成共用一个 `TurnOutcome` | 循环化之后 outcome 需要按步累积 |

**结论**：阶段 1 的结构能跑通三条路，但**它是一条流水线，不是 Agent**。
你这次要求升级为真正的 Observe → Decide → Tool Call → Observe → Decide → Final，**必须重写主流程**。

### A2. P4 Runtime（`app/agent/runtime.py`，850+ 行）

```
RuntimeState: LOAD_STATE → LOAD_MEMORY → RETRIEVE → DECIDE_ACTION
              → EXECUTE_ACTION → WAIT_USER → ASSESS → UPDATE_STATE → NEXT_TURN
```

**它是确定性的固定流水线**：

- 一轮里 `DECIDE_ACTION` **只执行一次**
- 状态顺序写死在 `submit_answer()` / `start()` 两个方法里
- 状态机编码的是**教学策略**（连对升难度、连错换讲法），不是通用工具编排

**可以复用的部分**：`ToolRunner` / `ToolBudget`（预算、超时、错误包装）、`_format_sources`、stage 回调机制。

**不能复用的部分**：状态机本身。它的"一次决策"是**刻意的设计**（教学动作一轮只能选一个，
这是你在 P4 定的硬约束）。把工具循环塞进去，会把"教学策略"和"工具编排"搅在一起。

→ **决策：新建通用 Agent Loop，P4 Runtime 一行不动。**

### A3. LLM Gateway（`app/core/llm.py`）

```python
@dataclass
class Message:
    role: str
    content: str          # ← 只有文本
```

方法：`chat` / `stream_chat` / `chat_json` / `_chat_json_raw`

**问题**：不支持多模态。图片无法进入消息。

**好消息**：`chat_json` 已内置 JSON 容错（剥 ```json 围栏、提取首个完整对象、失败重试），
**这正好是结构化 Tool Calling 需要的地基**。

### A4. RAG（`rag_service.retrieve_knowledge`）

```python
async def retrieve_knowledge(question, *, document_ids=None, top_k=None, ...) -> list[RagSource]
```

已经是干净的入口，**直接包成 Tool 即可**，不需要改动。

### A5. WebSearchProvider（`app/search/provider.py`，阶段 1 写的）

```
RealWebSearchProvider  → 包装 TavilyClient
MockWebSearchProvider  → 离线
MCPWebSearchProvider   → 抛出 NotImplementedError（接口位）
```

**问题**：
- `MCPWebSearchProvider` 是空的
- `capabilities()` 只回报 `provider` / `available` / `simulated`，**没有"实际用了哪个"的运行期信息**
- 没有"MCP 失败回退 Tavily"的逻辑

### A6. Tool Registry（`app/agent/tools/registry.py`）

```
ToolBudget(max_calls=3, max_seconds=...)  → exhausted / exhausted_reason()
ToolRunner.call(name, func, *, counted=True, **kwargs)  → ToolOutcome
ToolRunner.state_op(...)                  → 不计入预算
```

**这是个好底子**，但要支撑"按名字调工具"，缺的是：

- 没有 **工具注册表**（名字 → Schema + 处理函数）
- 没有 **Schema 描述**（让模型知道有哪些工具、参数是什么）
- `call()` 要求调用方把 `func` 传进来 —— 这是"我指定调哪个函数"，
  而 Agent 需要的是"模型说调哪个工具，我去查表"

→ **决策：在 registry.py 里新增 `ToolSpec` / `ToolRegistry`，`ToolRunner` 保持原样复用。**

## C. Agent Runtime / Tool Registry 架构

### C1. Agent Loop（新增 `app/agent/runtime_loop.py`）

```
        ┌─────────────────────────────────────────────┐
        │                                             │
  START → OBSERVE ──→ DECIDE ──→ 有 tool? ──yes──→ EXECUTE → OBSERVE_RESULT ──┐
            ↑                        │                                          │
            │                        no                                         │
            │                        ↓                                          │
            └────── 达到上限 ───── FINAL_ANSWER ←────────────────────────────────┘
```

**状态枚举**

```python
class LoopState(StrEnum):
    OBSERVE = "OBSERVE"              # 组装当前观察：问题 + 历史 + 已获得的结果
    DECIDE = "DECIDE"                # 模型决定：调哪个工具，或者直接回答
    EXECUTE = "EXECUTE"              # 执行工具（经 ToolRunner，受预算/超时约束）
    OBSERVE_RESULT = "OBSERVE_RESULT"# 把工具结果并入观察集
    FINAL_ANSWER = "FINAL_ANSWER"    # 流式生成最终回答
    DONE = "DONE"
```

**与 P4 的关键差异**：`DECIDE` 在循环里**会被执行多次**（每次看到新结果后重新判断）。

### C2. 硬限制（三条，缺一不可）

```python
MAX_STEPS       = 6     # 循环总轮数（含 FINAL_ANSWER）
MAX_TOOL_CALLS  = 3     # 与 P4 一致，直接复用 ToolBudget 的语义
TOTAL_TIMEOUT   = 30.0  # 整轮墙钟上限，与 P4 的 30s 一致
```

**为什么三个都要**：

- 只有 `MAX_TOOL_CALLS` → 模型可以反复"不调工具但不回答"，空转
- 只有 `MAX_STEPS` → 一次 step 里可能并发调多个工具，累计成本失控
- 没有 `TOTAL_TIMEOUT` → 单次工具都很快但次数多时，用户仍会等很久

**超限行为**：**不是报错，是降级到 `FINAL_ANSWER`** ——
用已有信息生成回答，并在回答里说明"还有一步没做完"。
这个原则和 P4 的"无论如何都能给用户一个回复"一致。

### C3. Tool 契约（放进现有 `registry.py`）

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str                      # 模型用这个名字指定工具
    description: str               # 给模型看的"什么时候用它"
    parameters: dict[str, Any]     # JSON Schema
    handler: Callable[..., Awaitable[ToolResult]]
    counted: bool = True           # 是否计入 ToolBudget
    timeout: float | None = None   # 覆盖默认工具超时
    requires: tuple[str, ...] = () # 前置能力，如 web_search 需要联网可用


@dataclass
class ToolResult:
    ok: bool
    #: 给模型看的**文本**（不是原始 JSON —— 模型读 JSON 容易跑偏）
    content: str = ""
    #: 给界面看的结构化摘要（右侧面板、SSE）
    display: dict[str, Any] = field(default_factory=dict)
    #: 引用/来源
    citations: list[dict[str, Any]] = field(default_factory=list)
    error: str | None = None
    #: 是否该重试（超时可重试，参数错误不该重试）
    retryable: bool = False
    elapsed_ms: int = 0
```

**`ToolResult.content` 是文本而不是 JSON，这是刻意的**：
模型读结构化 JSON 时容易把字段名当内容讲出来（"根据 url 字段…"）。
给一段排版好的文本，它讲出来的东西才像人话。

### C4. 四个 Tool（统一进 Registry）

| Tool | 复用 | counted | 说明 |
|---|---|---|---|
| `retrieve_knowledge` | `rag_service.retrieve_knowledge` | ✅ | 检索用户资料 |
| `web_search` | `WebSearchProvider`（新：MCP/Tavily 双后端） | ✅ | 联网 |
| `image_analysis` | **新**：多模态 LLM | ✅ | 看图（2.2 引入） |
| `document_analysis` | **新**：从已解析的资料里取指定章节/页 | ✅ | "讲讲第三章"（2.2 引入） |

**`if/else` 路由消失**：主流程只剩"查表 → 执行 → 记结果"。
加第五个工具只需要 `register()` 一次。

### C5. 结构化 Tool Calling 的协议（重要取舍）

**沿用项目既有的 JSON 通道，不引原生 function calling。**

`registry.py` 里已经有一段论证（"为什么不把 Tool 做成原生 function calling"）：
各家供应商支持程度不一、会多一轮往返、与 P1/P2/P4 的 `chat_json` 是同一套通道。

阶段 2 沿用这条路线，但把它做成**真正的工具调用协议**：

```json
{"thought": "资料里没讲到虚拟线程的现状", "tool": "web_search",
 "arguments": {"query": "Java 25 虚拟线程 变化"}}

{"thought": "资料和联网都拿到了，可以回答了", "final": true}
```

⚠️ **我要如实说明这里的权衡**：

- 原生 function calling 在多数供应商上**模型的工具选择准确率更高**
- 但改用原生要动 Gateway（`tools` 参数、`tool_calls` 解析、多轮消息格式），
  并波及 P1/P2/P4 所有 `chat_json` 调用点 —— 与"不破坏现有"冲突

**建议**：本阶段用 JSON 通道（与项目一致、可测、零破坏）。
若实测发现模型的工具选择质量不够，**再把 Gateway 的 `tools` 支持作为一个独立小阶段**，
而不是顺手改掉。这与我在阶段 1 处理"要不要引多模态"的原则一致：**扩展，不重写**。

### D2. MCP Client 的连接方式

**首选：远程 streamable HTTP**

```python
# 伪代码，说明协议步骤
POST https://mcp.tavily.com/mcp/
Headers: Authorization: Bearer <TAVILY_API_KEY>
         Content-Type: application/json
         Accept: application/json, text/event-stream

① {"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}
② {"jsonrpc":"2.0","method":"notifications/initialized"}
③ {"jsonrpc":"2.0","id":2,"method":"tools/list"}
④ {"jsonrpc":"2.0","id":3,"method":"tools/call",
    "params":{"name":"tavily_search","arguments":{"query":"...","max_results":5}}}
```

**响应是 SSE 包装的**（`event: message\ndata: {...}`），要剥壳后解析。

**实现选择**：

| 方案 | 优劣 |
|---|---|
| **用官方 Python SDK `mcp`** | 协议细节（SSE 解帧、会话、错误码）由 SDK 处理；**推荐** |
| 手写 JSON-RPC over HTTP | 零依赖，但要自己处理 SSE 帧、错误语义、协议版本 —— 不值得 |

⚠️ **实测风险**：本机 `mcp` SDK **未安装**，需 `pip install mcp`。
另外本机有已知的 npm 问题（见 D8 的风险说明），但**远程 HTTP 完全不需要 npm**。

**备选：本地 stdio**

```json
{"command":"npx","args":["-y","tavily-mcp@latest"],
 "env":{"TAVILY_API_KEY":"..."}}
```

**我不推荐作为首选**，理由见 D8。

### D4. MCP 与 Tavily 的切换

新增配置：

```bash
# mcp   = 只用 MCP（不可用则明确失败，不偷偷换）
# tavily= 只用 Tavily REST（保持阶段 1 行为，可随时回退）
# auto  = 优先 MCP，不可用则用 Tavily 并上报回退原因   ← 默认
WEB_SEARCH_BACKEND=auto
MCP_WEB_SEARCH_TRANSPORT=http
MCP_WEB_SEARCH_URL=https://mcp.tavily.com/mcp/
MCP_TIMEOUT_S=20
```

**为什么 `auto` 是默认**：用户不关心走哪条路，但**系统必须知道**。
所以 `auto` 的回退不是静默的 —— 它会产生一条 `fallback_reason`，进 SSE、进日志、进能力自检。

### D5. MCP 不可用时的回退

```
MCP 失败
  ├─ 连接失败 / 401 / 超时 / 协议错误
  │    → auto: 回退 Tavily，上报 fallback_reason="mcp_unreachable: ..."
  │    → mcp : 直接失败，明确告诉用户"联网服务不可用"
  └─ tools/list 里没有 tavily_search
       → **不回退**，报配置错误
         （这是"接错了"，不是"网络问题"，静默回退会把配置错误藏起来）
```

**最后一条是刻意的**：工具名不存在属于**配置/兼容性错误**，
如果也走静默回退，那么"文档写错一个字符"就会永远被掩盖成"网络偶尔不好"。

### D6. UI / SSE 如何显示实际用的是哪个

**每个 `citation` / `source` 事件加 `provider` 字段**：

```json
{"event":"citation",
 "data":{"kind":"web","title":"...","url":"...",
         "provider":"mcp",              ← 实际用的
         "provider_detail":"tavily-mcp v4.0.4",
         "fell_back":false,
         "fallback_reason":null}}
```

```json
{"event":"citation",
 "data":{"kind":"web","title":"...","url":"...",
         "provider":"tavily",           ← 回退后的实际后端
         "fell_back":true,
         "fallback_reason":"mcp_unreachable: connect timeout"}}
```

**界面上的呈现**（右侧"这一轮参考了什么"面板）：

```
联网查到 5 条参考              ← 正常
联网查到 5 条参考 · 经由 MCP    ← provider=mcp 时加一行小字

联网查到 5 条参考              ← 回退时
  ⚠ 首选服务没连上，已改用备用通道  ← fell_back=true 时才出现
```

**为什么要把回退显示出来**：它是**运维信号**。
如果 MCP 一直悄悄回退，你会以为 MCP 在工作，直到某天 Tavily 也不可用才发现。

### D7. 如何测试"确实经过 MCP 搜索"

你特别强调"不是代码里存在 MCP Provider 就算完成"。所以验收分四层：

**① 协议级证据（最关键）**

用一个包装 transport 的探针记录整轮 RPC：

```python
assert recorder.methods == ["initialize", "notifications/initialized",
                            "tools/list", "tools/call"]
assert recorder.server_info["name"] == "tavily-mcp"     # 从 initialize 响应里读的
assert "tavily_search" in recorder.tools_list_names     # 从 tools/list 读的，不是硬编码
assert recorder.call_params["name"] == "tavily_search"
```

**② 结果形状差异**

MCP 的 `tavily_search` 返回的是 **`content[0].text` 里的一段 JSON 字符串**，
而 Tavily REST 返回的是**已解析的对象**。

→ 断言"结果经由 MCP 解析路径"：`result.raw_json_string is not None`（只有 MCP 路径有这个中间层）。

**③ 服务端标识**

MCP 响应里带 server 的 `serverInfo.version`（实测 `4.0.4`）与请求 ID。
把它记进 `ToolResult.display`，能力自检接口能查到。

**④ 负向测试（防止"静默冒充"）**

| 场景 | 期望 |
|---|---|
| `WEB_SEARCH_BACKEND=mcp` + 错误 Key | **失败**，不回退，SSE 明确说连不上 |
| `WEB_SEARCH_BACKEND=auto` + 错误 Key | 回退 Tavily，`fell_back=true` + `fallback_reason` 非空 |
| MCP 返回的 tools/list 里没有 `tavily_search` | **不回退**，报配置错误 |
| `WEB_SEARCH_BACKEND=tavily` | 完全不发起 MCP 请求（断言 recorder 为空） |

**⑤ 浏览器端**

点一次联网提问，右侧面板**肉眼可见"经由 MCP"**，且能力自检接口返回
`mcp: {available: true, verified_tools: ["tavily_search"]}`。

### D8. ⚠️ 风险与未验证项（如实说明）

| 项 | 状态 |
|---|---|
| 远程 HTTP 端点 | ✅ **已实测**（initialize / tools/list / tools/call 全部成功） |
| 本地 stdio（`npx -y tavily-mcp`） | ❌ **未验证**。且本机有已知 npm 问题（项目目录下 `npm install` 静默失败），所以**不推荐作为首选** |

### G1. 三个真正 Agent 场景（你点名的）

#### 场景 1：普通问题，无需工具

```
"根据我的资料讲讲虚拟线程，资料里没有的再联网"
期望的 trace：
  step 1  DECIDE   → retrieve_knowledge
  step 2  OBSERVE  → 资料只讲到基础概念，没有"Java 25 的变化"
  step 3  DECIDE   → web_search          ← **这里证明是循环，不是流水线**
  step 4  OBSERVE  → 拿到联网结果
  step 5  DECIDE   → final
  step 6  FINAL_ANSWER
断言：
  · decide 次数 ≥ 3            ← 流水线做不到
  · 工具调用序列 == [retrieve_knowledge, web_search]
  · 回答里同时出现资料页码出处与网页链接
  · tool_calls == 2（≤ MAX_TOOL_CALLS）
```

#### 场景 3：上传图片

```
上传截图 + "帮我解释这段代码"
期望：
  step 1  DECIDE   → image_analysis
  step 2  OBSERVE  → 识别出代码内容
  step 3  DECIDE   → final（图片信息已足够）
  step 4  FINAL_ANSWER（解释代码）
断言：
  · 回答包含图片里真实存在的标识符（**证明真的看了图**，不是编的）
  · 消息进多模态通道（断言 Gateway 收到的 parts 里有 image_url）
```

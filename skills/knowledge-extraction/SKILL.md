# 知识点抽取

## 1. 目的

从带页码的文本块中，抽取**结构化、可考查、可溯源**的知识点。

三个形容词缺一不可：

- **结构化** —— 固定 Schema，供 P2 关系构建、P3 向量检索、P4 Tutor Agent 直接消费。
- **可考查** —— 粒度必须能落到「出题」这个动作上，否则对教学无用。
- **可溯源** —— 每个知识点都能点回原文页码。这是本项目区别于普通 AI 问答的核心。

## 2. 输入

| 输入 | 说明 |
|---|---|
| `chunks` | 同一文档的文本块，含 `chunk_index`、`page_start`、`page_end`、`heading_path` |
| `existing_titles` | **本文档已抽取的知识点标题列表**，用于跨批次去重 |

**批次策略**：优先把**同一 `heading_path` 下**的相邻块合成一批；一批 3–5 个块且总长 ≤ 4000 字符。
超出则从块边界切分（不切块本身）。这样同一章节的上下文完整，抽出的知识点内部一致。

## 3. 输出契约

每个知识点严格遵循下面的 Schema：

```json
{
  "title": "进程与线程的区别",
  "summary": "进程是资源分配的基本单位，线程是 CPU 调度的基本单位。",
  "details": "## 核心区别\n\n| 维度 | 进程 | 线程 |\n|---|---|---|\n| 资源 | 独立地址空间 | 共享所属进程 |\n| 开销 | 创建/切换大 | 小 |\n\n**要点**：同一进程内的线程共享代码段、数据段与打开的文件。",
  "key_points": ["进程拥有独立地址空间", "线程共享所属进程的资源", "线程切换开销小于进程"],
  "difficulty": 2,
  "importance": 5,
  "confidence": 0.95,
  "tags": ["操作系统", "并发"],
  "source_chunk_indexes": [3, 4],
  "source_pages": [2, 3],
  "heading_path": ["第3章 进程管理", "3.1 进程与线程"]
}
```

字段约束：

| 字段 | 约束 |
|---|---|
| `title` | ≤ 20 字，**名词短语**（不要"关于……的说明"这类句式） |
| `summary` | ≤ 60 字，一句话讲清「是什么」 |
| `details` | Markdown，150–400 字，含定义 + 要点 + 例子，可含表格与公式 |
| `key_points` | 2–4 条，每条 ≤ 25 字 |
| `difficulty` | 1–5 整数 |
| `importance` | 1–5 整数 |
| `confidence` | 0.0–1.0，两位小数 |
| `tags` | ≤ 3 个 |
| `source_chunk_indexes` | **至少 1 个**，且必须来自本批输入 |
| `source_pages` | 由引用的 chunk 页码推导，**禁止编造** |

## 4. 粒度规范（最容易做错的地方）

**判定准则：如果一个知识点不能用 1–2 个问题考完，就说明粒度太粗；如果多个知识点回答的是
同一个问题，就说明粒度太细。**

| 反例 | 问题 | 修正 |
|---|---|---|
| 「第3章 进程管理」 | 太大，包含十几个考点 | 按小节拆成「进程的概念」「进程状态转换」「PCB」…… |
| 「queue 的 enqueue 方法」 | 太小，是操作而非考点 | 合并为「队列的入队与出队操作」 |
| 「页表的作用」+「页表的结构」+「页表的存放位置」 | 三条讲的是同一件事 | 合并为「页表」一个知识点 |
| 「进程与线程的区别」 | 恰好是一个可考查的对比类考点 | ✅ 保持 |

## 5. 难度标注标准

| 值 | 含义 | 判定问句 |
|---|---|---|
| 1 | 识记 | 只需要记住定义/名词？ |
| 2 | 理解 | 能用自己的话解释？ |
| 3 | 应用 | 能套用这个知识解题？ |
| 4 | 分析 | 能比较多种方案或推导过程？ |
| 5 | 综合/创造 | 能设计、证明或迁移到新场景？ |

## 6. 重要度标注标准

| 值 | 含义 |
|---|---|
| 5 | 教材明确标注的核心概念 / 考点 |
| 4 | 章节主干内容 |
| 3 | 支撑性内容（帮助理解但不直接考） |
| 2 | 举例、补充说明 |
| 1 | 边角信息、历史背景、作者按 |

**判定依据只能来自材料本身**（加粗、"注意"、"考点"、例题、图示标题），不得凭模型对学科的
主观印象打分。材料中信息不足时，取中位数 3。

## 7. 置信度标注标准

`confidence` 表示**该知识点是否忠实于原文**，不是"模型有多确定"：

| 区间 | 含义 |
|---|---|
| 0.90–1.00 | 原文直接陈述，可直接引用 |
| 0.70–0.89 | 由原文可推导（如原文给了两个例子，归纳出一般规律） |
| 0.50–0.69 | 需要外部知识补充才能完整阐述 |
| < 0.50 | 原文信息不足，**不应产出该知识点**；若产出需在 details 中显式标注不确定 |

## 8. 溯源规则（硬约束）

1. 每个知识点**必须**至少引用一个 `source_chunk_indexes`，为空的知识点直接丢弃。
2. `source_pages` 必须由被引用 chunk 的页码**推导**，禁止模型自己写页码。
   实现上：模型只输出 `source_chunk_indexes`，`source_pages` 由代码回填 —— **不给模型编造的机会**。
3. `details` 中不得引入原文没有的事实。确有必要补充背景时，用 `**补充**：` 前缀显式标注。
4. 引用的 chunk 必须属于本批次输入，越界引用视为无效并丢弃该条。

> 第 2 条是设计上的偷懒换安全：与其在提示词里反复叮嘱"不要编页码"，不如让模型根本没有
> 输出页码的字段，页码全部由代码从 chunk 反查。**能靠结构避免的错误，不要靠提示词避免。**

## 9. 去重规则

分两层：

**第一层 · 提示词内联合去重（推荐）**
把 `existing_titles` 传给模型，明确要求「下列标题已存在，不要重复抽取」。
成本为零，能挡掉绝大多数重复。

**第二层 · 产出后归一化去重（兜底）**
对全部知识点做标题归一化（去空格、去标点、转小写、去除"的/与/及"等虚词）：
- 归一化后**完全一致** → 合并

**第三层 · 数据库唯一索引**
`UNIQUE(document_id, title_norm)` 作为最后一道防线。前两层漏掉的重复会在写入时报冲突，
流水线降级为逐条写入并跳过重复项，因此**绝不会**出现重复知识点。

> **P1 的实现边界**：只做「归一化后完全一致」的合并。
> 「一方包含另一方」交给 LLM 判定虽然更彻底，但极易**过度合并** ——
> 「进程」会被并进「进程与线程」，「页表」会被并进「页表与快表」，
> 而它们其实是不同的考点。因此包含关系的判定推迟到 P2 引入关系构建时，
> 与「前置/包含」关系一起处理（那里本来就需要判断知识点之间的层级）。

**合并时的字段取舍**：

| 字段 | 取法 |
|---|---|
| `details` | 并集（去重后拼接） |
| `key_points` | 并集，最多保留 4 条 |
| `source_chunk_indexes` / `source_pages` | 并集 |
| `difficulty` | 取**较大**者（能考更难的那个说明理解更深） |
| `importance` | 取**较大**者 |
| `confidence` | 取**较小**者（保守） |
| `tags` | 并集，最多 3 个 |

## 10. 质量闸门

产出后自检，任一项不通过则该批标记 `partial` 并记 warning，**但不让整份文档失败**：

| 检查 | 阈值 | 不通过的处置 |
|---|---|---|
| 本批知识点数量 | 1–5 条 | 0 条 → 记 `EMPTY_BATCH`；> 5 条 → 记 `TOO_FINE_GRAINED` |
| **整篇产出** | 至少 1 条 | 全部批次都为 0 时记 `NO_KNOWLEDGE_POINT`，并说明可用块数与常见原因 |
| `source_chunk_indexes` 非空 | 全部 | 丢弃该条并计数 |
| `difficulty` / `importance` 在 1–5 | 全部 | 钳制到边界值 |
| `title` 长度 ≤ 20 | 全部 | 截断并记 warning |
| 结构化输出解析成功 | 必须 | 重试 1 次；再失败则该批记 `LLM_PARSE_FAILED`，跳过 |

**为什么要单独有一条「整篇产出」检查**：每批记 `EMPTY_BATCH` 只是把问题摊开，
用户面对 10 条 `EMPTY_BATCH` 仍然不知道该做什么。补一条文档级提示说明
「共 N 批 / M 个可用文本块但没有产出」，并点出常见原因（文本层损坏、内容全是图表、
材料过零碎），才能把故障转成可排查的现象。上游解析层的 `SUSPECT_TEXT_LAYER` 与这条配合使用。

## 11. 提示词结构

提示词模板落地在 `apps/api/app/agent/prompts/extract_knowledge_points.md`，结构如下：

```
【系统】
你是学习资料的知识点抽取引擎。
只输出 JSON，不输出任何解释文字。

输出 Schema：
{完整 JSON Schema，含字段类型与约束}

粒度规范：{第 4 节内容}
难度标准：{第 5 节表格}
重要度标准：{第 6 节表格}
置信度标准：{第 7 节表格}

硬约束（违反则整条作废）：
- source_chunk_indexes 必须来自本次输入，至少 1 个
- 不要输出页码字段，页码由系统回填
- details 不得引入原文没有的事实，必要时用「**补充**：」标注

【用户】
文档名：{{file_name}}
章节路径：{{heading_path}}
已存在的知识点标题（不要重复）：{{existing_titles}}

待抽取内容：
<<<chunk_index=3 | page=2>>>
{chunk 3 正文}
<<<chunk_index=4 | page=2>>>
{chunk 4 正文}

请输出 JSON：{"knowledge_points": [...]}
```

调用方式：`response_format={"type":"json_object"}`（DeepSeek / Qwen / GLM 均支持）。
提供商不支持时降级为「仅提示词约束 + 解析容错」（剥离 ```json 围栏、提取首个完整 JSON 对象）。

## 12. 验收标准（P1）

- [ ] 一份 10 页课程 PDF 产出 ≥ 15 个知识点
- [ ] 每个知识点都带 `source_pages`，且页码在原文档中真实存在
- [ ] 前端点击来源页码 → 展示对应 chunk 原文
- [ ] 无「整章一个知识点」或「一个符号一个知识点」的粒度失控
- [ ] 同一知识点不重复出现（去重两层生效）
- [ ] `difficulty` / `importance` 确实呈现分布，而非全为 3
- [ ] 结构化输出解析失败时：重试 1 次 → 仍失败则跳过该批并记 warning，**不中断整份文档**
- [ ] 在 mock 模式下可端到端跑通（不消耗 API 额度即可回归测试）

## 13. 与其他阶段的边界

本 Skill **只做抽取**，明确不做：

| 不做 | 归属阶段 |
|---|---|
| 判断知识点之间是否有前置/包含关系 | P2 |
| 可信度校验与联网核验 | P2 |
| 向量化与检索 | P3 |
| 出题、评估作答、决定教学动作 | P4 |

但输出的 Schema 必须**预留**这些阶段的字段：`confidence` 与 `verify_status` 给 P2，
`source_chunk_indexes` 给 P3 做引用、给 P4 做讲解时的原文依据。
